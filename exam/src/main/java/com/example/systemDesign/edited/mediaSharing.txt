ADR-003: انتخاب مکانیزم Adaptive Bitrate Streaming
وضعیت: پذیرفته شده

زمینه:
تصور کنید کاربر با اینترنت ۴G شروع می کنه به دیدن یک ویدیو. کیفیت ۱۰۸۰p رو انتخاب می کند
و وسط ویدیو، یهو اینترنتش ضعیف می شود. اگه ویدیو فقط یه کیفیت داشته باشه، دو تا اتفاق می افته:
یا ویدیو قطع می شه و کاربر باید صبر کنه تا دوباره وصل بشه.
یا Buffer می خوره؛ یعنی ویدیو متوقف می شه و اون دایرهٔ چرخون چرخون وسط صفحه ظاهر می شه.


تصمیم:
مفهوم HLS یا HTTP Live Streaming یک پروتکل استریمینگه که اپل برای iOS و Safari ساخت.
این پروتکل ویدیو رو به یه سری قطعهٔ کوچیک (معمولاً ۶ ثانیه ای) تقسیم می کنه و این قطعات رو از طریق HTTP معمولی تحویل می دهد.
یعنی به جای اینکه کل ویدیو یه فایل بزرگ باشه، قطعاتٔ کوچیک داریم که کاربر یکی یکی دانلود می کنه.

مفهوم DASH یا Dynamic Adaptive Streaming over HTTP یه استاندارد باز (ISO/IEC) هست که کارش شبیه HLS هست.
ویدیو رو به قطعات کوچیک تقسیم می کند و با HTTP تحویل می دهد.
تفاوتش با HLS تو فرمت فایل هاست (m4s به جای ts) و تو اینکه استانداردش بازتره و توسط چند شرکت با هم توسعه داده شده.

و Master Playlist هم یک فایل کوچیک متنی (m3u8 برای HLS و mpd برای DASH) که لیست کیفیت های موجود رو نگه می دارد.

از HLS + DASH + Master Playlist استفاده می کنیم.

دلیل تصمیم:
کلاینت از یه الگوریتم به اسم ABR (Adaptive Bitrate) استفاده می کنه. چند مدل مختلف داره:
Throughput-based: بر اساس سرعت دانلود فعلی. اگه سرعت بالا باشه، کیفیت بالا می گیره.
Buffer-based: بر اساس میزان Buffer موجود. اگه Buffer پر باشه، کیفیت بالا می گیره.
Hybrid: ترکیب هر دو (الگوریتم هایی مثل BOLA و DYNAMIC). اینا معمولاً بهترین نتیجه رو می دن.
الگوریتم تو هر لحظه یه کیفیت انتخاب می کند و قطعهٔ بعدی رو با اون کیفیت دانلود می شود.
کاربر حتی متوجه نمی شود که کیفیت در حال تغییر است فقط می بیند ویدیو بدون قطعی و بدون Buffer پیش می رود.

مزایا:
Adaptive Bitrate (سوییچ خودکار)
پشتیبانی از همه ی پلتفرم ها
کاهش Buffer
تجربه ی روان

معایب:
پیچیدگی تولید HLS/DASH
حجم ذخیره سازی بیشتر (چند کیفیت)
نیاز به CDN
تأخیر اولیه

ADR-004: انتخاب مکانیزم برای ذخیره سازی Metadata و جستجو

زمینه:
میلیون ها ویدیو داریم. کاربران می خواهند بر اساس عنوان، توضیحات، تگ، سازنده، دسته بندی و جستجو کنند.
 اگه از دیتابیس رابطه ای استفاده کنیم، Full-Text Search کند می شود. از طرف دیگر، Metadata باید ACID باشه.

تصمیم:
استفاده از دو دیتابیس مکمل هم:

Elasticsearch به عنوان موتور جستجو برای Full-Text Search و Faceted Search.
CDC(Change Data Capture) Debezium + Kafka برای همگام سازی این دو.

دلیل تصمیم:
دیتابیس PostgreSQL یه دیتابیس رابطه ای با ACID کامله است.
و Elasticsearch یه موتور جستجوی تخصصی با Inverted Index است. یعنی برای هر کلمه، لیستی از ویدیوهایی که اون کلمه رو دارن ذخیره می کند
 وبه جای اینکه بره تک تک رکوردها رو بخواد و جستجو کند (که این کار خیلی کند است)
.مستقیم ایندکس را درآورده و نتیجه رو در چند میلی ثانیه برمی گرداند


مزایا:

جستجوی فوق سریع: زیر ۱۰۰ میلی ثانیه با Elasticsearch.
Faceted Search: فیلترهای ترکیبی پیچیده.
هماهنگی خودکار: با CDC، نیازی به Sync دستی نیست.
تحمل خطا: اگه Elasticsearch بخوابه، داده تو Kafka می مونه.
Replay ممکن: می تونیم Index رو دوباره بسازیم.
مقیاس پذیری: هر دو دیتابیس به صورت مستقل مقیاس پذیرن.
معایب:
پیچیدگی زیرساخت: سه سرویس درگیر (PostgreSQL + Debezium + Kafka + Elasticsearch).
تأخیر Sync: چند صد میلی ثانیه بین ذخیره و ایندکس شدن.
هزینه Elasticsearch: RAM و Cluster هزینه بره.
مدیریت دو دیتابیس: نگهداری و Monitoring سخت تر.
Eventual Consistency: Elasticsearch نهایتاً با PostgreSQL هماهنگ می شه، نه آنی.

ADR-006: انتخاب مکانیزم Live Streaming
وضعیت: پذیرفته شده

زمینه:
استریمرها می خواهند Live Stream کنند.
 تأخیر باید زیر ۵ ثانیه باشه. اگه از HLS معمولی استفاده کنیم، تأخیر ۳۰ ثانیه می شه که برای Live تعاملی مناسب نیست.

تصمیم:
از RTMP (Ingest) + LL-HLS (Low-Latency HLS) + WebRTC (برای تأخیر بسیار کم) استفاده می کنیم.

دلیل تصمیم:
بعضی Live ها نیاز به تعامل لحظه ای دارن، مثل مصاحبهٔ دوطرفه، پرسش و پاسخ زنده، یا کلاس آنلاین. اینجا حتی ۲ ثانیه تأخیر هم زیاده
و WebRTC تأخیرش زیر ۱ ثانیه است (تقریباً همون لحظه). چرا؟ چون WebRTC روی UDP کار می کند. عیبش اینه که برای میلیون ها بیننده مقیاس پذیر نیست
و نیاز به SFU (Selective Forwarding Unit) داره که هزینه و پیچیدگی داره.
پس WebRTC رو برای سناریوهایی استفاده می کنیم که تعداد بیننده کمه ولی تعامل حیاتیه.

جریان کار به این شکله:
استریمر با OBS استریم رو با RTMP می فرسته به سرور ما.
سرور RTMP رو دریافت می کنه و بسته به نوع Live، تصمیم می گیره:
اگه Live عمومی و پر بیننده ست → تبدیل به LL-HLS و پخش از طریق CDN.
اگه Live تعاملی و کم بیننده ست → تبدیل به WebRTC و پخش مستقیم.
اگه هر دو لازمه → هم LL-HLS برای بیننده های عادی، هم WebRTC برای میزبان و مهمان های ویژه.
کلاینت بر اساس لینکی که دریافت می کنه، پخش رو شروع می کنه.

مزایا:
تأخیر پایین (۲ تا ۵ ثانیه با LL-HLS)
پشتیبانی از همه ی پلتفرم ها
مقیاس پذیری با CDN
کیفیت بالا
معایب:
پیچیدگی LL-HLS
نیاز به CDN مخصوص
هزینه ی بالا
Debugging سخت

ADR-007: انتخاب مکانیزم Comment و Interaction
وضعیت: پذیرفته شده

زمینه:
کاربران می خواهند زیر ویدیو کامنت بذارند، لایک کنن، ریپلای بدن.
 تعداد کامنت ها ممکنه میلیونی بشه (مثلاً زیر یه ویدیو وایرال). باید Query سریع باشه و Real-time Update.

تصمیم:
ترکیب سه گانه ی Cassandra + Redis + Kafka:
Cassandra برای ذخیره ی دائمی کامنت ها و ریپلای ها.
Redis برای کش کردن کامنت های پرطرفدار و شمارنده ها.
Kafka برای انتشار رویدادهای جدید و هماهنگی Real-time.

دلیل تصمیم:
Cassandra برای Write سنگین ساخته شده.

و Redis چون In-Memory هست، پاسخش زیر ۱ میلی ثانیه است در نتیجه شمارنده ها (تعداد لایک، تعداد ریپلای) هم تو Redis نگه داری می شوند.
چون اینا دائماً در حال تغییرن، اگه هر تغییر مستقیم بره به Cassandra، بار Write الکی زیاد می شود.
کاربر که کامنت جدید می ذاره، یه Event به Kafka می فرسته: «کامنت جدیدی روی ویدیوی X ثبت شد» و به همه علاقه مندان فرستاده  می شود.


مزایا:
Write سریع (Cassandra)
Query سریع (Redis Cache)
Real-time Update (Kafka)
مقیاس پذیری خطی
معایب:
پیچیدگی سه گانه
Eventual Consistency
نیاز به Cache Invalidation
هزینه ی Redis

ADR-010: انتخاب مکانیزم تحمل خطا و High Availability
وضعیت: پذیرفته شده

زمینه:
پلتفرم باید هفت روز هفته و هر روز 24 ساعت در دسترس باشه.
اگه یه Region از کار بیفته، کاربران نباید قطعی بشوند.
و باید Availability تضمین شود.

تصمیم:
معماری Multi-Region Active-Active با Load Balancer و Replication در Cassandra و PostgreSQL.

دلیل تصمیم:
چون Active-Active یعنی هر دو Region همزمان ترافیک می‌گیرن.
اگه یکی Down بشه، Global Load Balancer خودکار ترافیک رو به Region دیگه می‌فرسته.

مزایا:
ایجادDowntime صفر در صورت خرابی یک Region (کاربران متوجه نمی‌شوند)
کاربرا به نزدیک‌ترین Region وصل می‌شن (Latency کمتر)
تحمل خرابی‌های بزرگ (زلزله، قطعی برق، حملات سایبری)

معایب:
هزینه زیرساخت زیاد (دو Region فعال)
پیچیدگی در Sync داده‌ها
نیاز به تیم SRE حرفه‌ای

موارد دیگر بررسی شده:
الف) Active-Passive:
مزایا:
هزینه کمتر (Region دوم فقط Standby)
پیاده‌سازی ساده‌تر
معایب:
بوجود آمدنDowntime در Failover (چند دقیقه تا چند ساعت)
Region دوم همیشه بیکار می‌مونه (هدر رفت منابع)
زمان ریکاوری بالا


ب) Single Region با Backup:
مزایا:
سادگی، هزینه کم
معایب:
Downtime طولانی در خرابی
کاربرای دور، Latency بالا
نقض SLA

ج) Multi-Cloud (AWS + GCP):
مزایا:
تحمل خرابی Provider
عدم Vendor Lock-in
معایب:
پیچیدگی بسیار بالا
هزینه چند برابر
Sync داده سخت‌تر

پیامدها:
مثبت:  Latency پایین برای کاربران
منفی: هزینه بالا، پیچیدگی عملیاتی، نیاز به تیم SRE
ریسک: Conflict در Replication → راه‌حل: Last-Write-Wins + CRDT برای داده‌های خاص

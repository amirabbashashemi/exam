ADR-001: معماری Multi-Region Active-Active برای High Availability
وضعیت: پذیرفته شده

زمینه:
پلتفرم باید هفت روز هفته و هر روز 24 ساعت در دسترس باشه.
اگه یه Region از کار بیفته، کاربران نباید قطعی بشوند.
و باید Availability تضمین شود.

تصمیم:
معماری Multi-Region Active-Active با Load Balancer و Replication در Cassandra و PostgreSQL.

دلیل تصمیم:
چون Active-Active یعنی هر دو Region همزمان ترافیک می‌گیرن.
اگه یکی Down بشه، Global Load Balancer خودکار ترافیک رو به Region دیگه می‌فرسته.

مزایا:
ایجادDowntime صفر در صورت خرابی یک Region (کاربران متوجه نمی‌شوند)
کاربرا به نزدیک‌ترین Region وصل می‌شن (Latency کمتر)
تحمل خرابی‌های بزرگ (زلزله، قطعی برق، حملات سایبری)

معایب:
هزینه زیرساخت زیاد (دو Region فعال)
پیچیدگی در Sync داده‌ها
نیاز به تیم SRE حرفه‌ای

موارد دیگر بررسی شده:
الف) Active-Passive:
مزایا:
هزینه کمتر (Region دوم فقط Standby)
پیاده‌سازی ساده‌تر
معایب:
بوجود آمدنDowntime در Failover (چند دقیقه تا چند ساعت)
Region دوم همیشه بیکار می‌مونه (هدر رفت منابع)
زمان ریکاوری بالا


ب) Single Region با Backup:
مزایا:
سادگی، هزینه کم
معایب:
Downtime طولانی در خرابی
کاربرای دور، Latency بالا
نقض SLA

ج) Multi-Cloud (AWS + GCP):
مزایا:
تحمل خرابی Provider
عدم Vendor Lock-in
معایب:
پیچیدگی بسیار بالا
هزینه چند برابر
Sync داده سخت‌تر

پیامدها:
مثبت:  Latency پایین برای کاربران
منفی: هزینه بالا، پیچیدگی عملیاتی، نیاز به تیم SRE
ریسک: Conflict در Replication → راه‌حل: Last-Write-Wins + CRDT برای داده‌های خاص

ADR-002: استراتژی Caching برای مقابله با بار سنگین
وضعیت: پذیرفته شده

زمینه:
موتور پیشنهاد دهنده باید برای میلیون‌ها کاربر پیشنهاد شخصی‌سازی‌شده تولید کنه.
اگه هر درخواست مستقیم به دیتابیس بره، زیر بار سنگین کارایی خودش را از دست می دهد.

تصمیم:
استفاده از Redis Cluster با استراتژی Cache-Aside و TTL مبتنی بر نوع داده:

پیشنهادات پرتکرار: TTL = ۵ دقیقه
پروفایل کاربر: TTL = ۳۰ دقیقه

دلیل تصمیم:
ابتدا داده در ردیس جستجو می شود اگر در ردیس وجود نداشت داده از دیتابیس لود می شود
که این امر باعث می شود درخواست‌ها از کش پاسخ ب‌گیرن و بار دیتابیس به شکل چشم گیری کاهش پیدا ‌کند.

مزایا:
کاهش بار روی دیتابیس
Latency بسیار پایین
مقیاس‌پذیری افقی با Redis Cluster
معایب:
Single Point of Failure (اگه Redis Cluster Down بشه)
مصرف RAM زیاد (هزینه)
Update داده در کس پیچیدگی دارد

موارد دیگر بررسی شده:
الف) بدون Cache (مستقیم به DB):
مزایا:
همیشه داده تازه (Consistency کامل)
سادگی پیاده‌سازی
معایب:
کندی زیر بار سنگین
دیتابیس به سرعت اشباع می‌شه
هزینه دیتابیس بالا

ب) Local Cache (In-Memory در هر سرویس):
مزایا:
سرعت فوق‌العاده (بدون Network)
بدون وابستگی به Redis
معایب:
محدودیت حافظه هر سرویس
ناهماهنگی بین Instanceها
Cache Invalidation سخت


ج) Memcached:
مزایا:
سادگی، سرعت بالا
Multi-threaded
معایب:
فقط Key-Value (بدون ساختار داده پیشرفته)
بدون Persistence
بدون Replication داخلی


پیامدها:
مثبت: بار دیتابیس ۱۰ برابر کمتر، Latency پایین
منفی: هزینه Redis Cluster، پیچیدگی Invalidation
ریسک: Redis Down → Fallback به دیتابیس + Rate Limiting

ADR-003: الگوهای Resilience (Circuit Breaker + Retry + Bulkhead)
وضعیت: پذیرفته شده

زمینه:
موتور پیشنهاددهنده به سرویس‌های خارجی وابسته است.
اگه یکی از این سرویس‌ها کند یا خراب بشه، درخواست‌ها صف می‌شن و کل سیستم از کار می‌افته.

تصمیم:
استفاده از Resilience4j با ترکیب سه الگو:
Circuit Breaker: قطع ارتباط بعد از ۵۰٪ خطا در ۱۰ ثانیه
Retry: ۳ بار با Exponential Backoff (۱s, ۲s, ۴s)
Bulkhead: Thread Pool جداگانه برای هر سرویس خارجی

دلیل تصمیم:
ماهیت Circuit Breaker جلوی Cascading Failure رو می‌گیره.
وRetry خطاهای موقت رو جبران می‌کنه.
وBulkhead تضمین می‌کنه که یه سرویس کندروی بقیه سرویس‌ها تاثیر نگذارد آنها نیز کند و کرش نکنند.

مزایا:
جلوگیری از Cascading Failure
بازیابی خودکار (بعد از رفع مشکل، مدار بسته می‌شه)
جداسازی منابع (یه سرویس خراب، بقیه رو خراب نمی‌کنه)

معایب:
تنظیم آستانه‌ها نیاز به تست و تجربه داره
Retry ممکنه سرویس مقصد رو Overload کنه
پیچیدگی Debugging (کدوم مرحله شکست خورد؟)


موارد دیگر بررسی شده:

الف) Retry ساده (بدون Circuit Breaker):
مزایا:
سادگی پیاده‌سازی
پوشش خطاهای موقت
معایب:
Retry Storm (اگه سرویس خراب باشه، بار بیشتر می‌شه)
Cascading Failure
بدون Fallback

ب) Timeout فقط:
مزایا:
سادگی
جلوگیری از انتظار بی‌نهایت
معایب:
کافی نیست (سرویس ممکنه کند بمونه ولی Down نشه)
Thread Pool اشباع می‌شه

ج) Bulkhead به تنهایی:
مزایا:
جداسازی منابع
جلوگیری از Exhaustion
معایب:
بدون قطع ارتباط با سرویس خراب
Retry نداره

پیامدها:
مثبت: مقاومت بالا در برابر خرابی، Fail Fast
منفی: پیچیدگی تنظیمات، نیاز به Monitoring دقیق
ریسک: آستانه اشتباه → Alert + بازبینی دوره‌ای

خطرناک (اگه اشتباه اجرا بشه، Production خراب می‌شه)

مزایا:

معایب:

ADR-009: معماری Tiered Storage برای داده‌های حجیم
وضعیت: پذیرفته شده

زمینه:
داده‌های کاربران و ارتبازات کاربران روز به روز زیاد می‌شود.
نگه‌داری همه چیز در PostgreSQL باعث کندی و هزینه بسیار بالا می باشد.
واز طرف دیگر، بعضی داده‌ها قدیمی‌ان و کم استفاده می‌شن ولی باید برای Audit در دسترس قرار داشته باشند
 اما بسیار کم استفاده می شوند

تصمیم:
Hot (۰-۶ ماه): PostgreSQL + Redis
Warm (۶ ماه - ۲ سال): Elasticsearch
Cold (> ۲ سال): S3 Glacier
Job شبانه برای انتقال خودکار
بازیابی از Glacier: ۳-۵ ساعت (با اطلاع‌رسانی)

دلیل تصمیم:
هر داده تو دیتابیسی که بر اساس تاریخ ایجاد مناسبه است ذخیره می‌شود.
 داده‌های اخیر باید سریع جستجو شوند و داده‌های قدیمی نیز در دسترس باشند و در storage کم هزینه نگهداری شوند

دلیل تصمیم:
با الگوی Soft Delete تمامی Foreign Keyها سالم باقی می مانند

مزایا:

Foreign Keyها سالم می‌مونن
Crypto-Shredding امنیت بالا

معایب:
پیچیدگی پیاده‌سازی (Job + Anonymization)

ADR-012: امنیت ارتباطات داخلی با mTLS و RBAC در API Gateway
وضعیت: پذیرفته شده

زمینه:
ارتباط بین میکروسرویس‌ها باید امن باشه.
اگه کسی به شبکه داخلی دسترسی پیدا کنه، نباید بتونه ترافیک رو شنود کنه یا خودشو جای یه سرویس جا بزنه.
از طرف دیگه، دسترسی‌ها باید بر اساس نقش کنترل بشه.

تصمیم:
mTLS (Mutual TLS) برای همه ارتباطات بین سرویس‌ها
Certificateهای X.509 از CA داخلی
RBAC در API Gateway (Kong)
JWT با Claim نقش برای Authorization
Certificate Rotation هر ۹۰ روز

دلیل تصمیم:
باmTLS هر سرویس یک Certificate معتبر دارد.
اگه مهاجم به شبکه دسترسی پیدا کنه، بدون Certificate نمی‌تواند خودش را جای سرویس جا بزنه و RBAC در Gateway یعنی کنترل دسترسی .

مزایا:
جلوگیری از Man-in-the-Middle
احراز هویت متقابل سرویس‌ها
کنترل دسترسی متمرکز (RBAC)
Certificate Rotation خودکار

معایب:
Overhead در CPU (رمزنگاری/رمزگشایی)
مدیریت Certificate پیچیده
Debugging سخت (ترافیک رمزنگاری‌شده)

مزایا:
سادگی
Overhead کمتر
معایب:
سرویس‌ها همدیگه رو تأیید نمی‌کنن
مهاجم می‌تونه خودشو جای سرویس جا بزنه
بدون Mutual Auth

مزایا:
سادگی
Performance بالا
معایب:

سادگی

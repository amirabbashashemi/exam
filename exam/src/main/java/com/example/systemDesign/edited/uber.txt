ADR-001: انتخاب مکانیزم Geospatial برای Matching
وضعیت: پذیرفته شده

زمینه:
وقتی مسافری درخواست می دهد، باید نزدیک ترین راننده های در دسترس پیدا شوند.
اگه از Query معمولی (مثلاً BETWEEN lat AND lng) استفاده کنیم، با میلیون ها راننده جواب این Query بسیار کند می شود.
در نتیجه باید یه مکانیزم سریع برای جستجوی مکانی داشته باشیم.

تصمیم:
استفاده از Redis GEO (GEOADD + GEOSEARCH) به همراه Geohashing.

دلیل تصمیم:
مفهموم Redis GEO یک ساختار داده خاص In-Memory هست که برای جستجوی مکانی بکار می رود.
دو تا دستور اصلی دارد:
GEOADD برای اضافه کردن یه نقطه با مختصات (longitude و latitude).
GEOSEARCH برای پیدا کردن نقاط تو یه شعاع مشخص از یه نقطه مرکزی.
و GEOSEARCH می تونه تو چند میلی ثانیه، راننده های تو شعاع مشخص (مثلا ۵ کیلومتر) را پیدا کند.
و Geohashing هم برای ذخیره سازی مکانی رستوران ها و راننده ها تو Elasticsearch استفاده می شه.

مزایا:
جستجوی مکانی سریع (زیر ۱۰ میلی ثانیه)
مقیاس پذیری بالا (In-Memory)
پشتیبانی از شعاع و محدوده
ادغام آسان با Redis Cluster
معایب:
Redis ممکنه Single Point of Failure بشه
حافظه ی محدود (نیاز به Cluster)
دقت Geohashing محدود (سطح ۹ = ~۵ متر)
نیاز به Sync با دیتابیس اصلی

معایب:
کندی با میلیون ها راننده
بار زیاد روی DB
نیاز به Index پیچیده

ب) Elasticsearch Geo-Point:
مزایا:
جستجوی سریع
ادغام با جستجو
معایب:
کندتر از Redis
برای Real-time مناسب نیست
هزینه ی بالا

ج) QuadTree در حافظه:
مزایا:
کنترل کامل
Performance بالا

ADR-002: انتخاب مکانیزم برای تخصیص راننده (Driver Assignment)
وضعیت: پذیرفته شده

زمینه:
وقتی دو یا چند مسافر به راننده نزدیک همزمان درخواست می دهند،
نباید هر دو به یک راننده تخصیص داده شوند. باید مطمئن باشیم یک راننده فقط به یک سفر تخصیص داده می شود.

تصمیم:
از Distributed Lock (Redis Redlock) + Optimistic Locking (PostgreSQL) استفاده می کنیم.

دلیل تصمیم:
مفهوم Redlock یه قفل توزیع شده ست که با SETNX و TTL کار می کنه.
وقتی چند مسافر همزمان درخواست می دهند، دستور SETNX  برای همه آنها در ردیس اجرا می شود
و جواب این دستور فقط برای یک درخواست 1 است در نتیجه راننده به یک مسافر اختصاص پیدا می کند
و همچنین از Optimistic Locking هم تو دیتابیس برای lock نهایی استفاده می کنیم.

مزایا:
جلوگیری از تخصیص دوگانه (Race Condition)
سرعت بالا (Redis In-Memory)
TTL خودکار (اگه مسافر منصرف شد، قفل آزاد می شه)
مقیاس پذیری
معایب:
Redlock تو شرایط Split-Brain ممکنه مشکل داشته باشه
نیاز به Redis Cluster با HA
پیچیدگی مدیریت TTL
اگه Redis Down بشه، تخصیص متوقف می شه

ADR-003: انتخاب مکانیزم برای Real-time Location Tracking
وضعیت: پذیرفته شده

زمینه:
مسافر می خواد موقعیت راننده رو روی نقشه ببینه. راننده هر چند ثانیه موقعیتش رو می فرسته. این داده باید Real-time به مسافر برسه و تأخیرش زیر ۵۰۰ میلی ثانیه باشه.

تصمیم:
از WebSocket + Redis Pub/Sub + TimescaleDB استفاده می کنیم.

دلیل تصمیم:
با WebSocket می توان یک ارتباط دوطرفه و امن (WSS) و با تاخیر بسیار کم ایجاد نمود.
و با استفاده از Redis می توان در بازه های 5 ثانیه ای موقعیت راننده را در ردیس ذخیره کرد
و تمام کسانی که آنرا track می کنند هم با زمان بسیار پایین آخرین موقعیت را از ردیس با تاخیر کم استخراج و مشاهده نمایند
و برای دخیره نهایی مسیر از دیتابیس TimescaleDB استفاده می کنیم زیرا
داده های GPS ذاتاً زمان محور هستن ( برای هر راننده، یه دنباله از نقاط با زمان ذخیره می شود)
. اگه اینا رو تو یه دیتابیس معمولی مثل PostgreSQL ذخیره کنیم، بعد از مدتی حجمشون نجومی میشه و کوئری ها کند میشن.
در نتیجه در TimescaleDB ذخیره می کنیم زیرا هم بر اساس زمان پارتیشن می شوند و هم امکان Compression دارد.

مزایا:
Real-time (تأخیر زیر ۱۰۰ میلی ثانیه)
مقیاس پذیری بالا با Redis Cluster
ذخیره ی GPS Trail برای تحلیل
Compression در TimescaleDB (۹۰٪ کاهش حجم)
معایب:
پیچیدگی WebSocket (Reconnection، Keep-alive)
Redis ممکنه Single Point of Failure بشه
هزینه ی TimescaleDB
نیاز به Connection Registry

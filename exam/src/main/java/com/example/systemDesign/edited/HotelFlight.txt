ADR-001: انتخاب دیتابیس برای ذخیره‌ی رزروها

وضعیت: پذیرفته شده

زمینه:
رزروها باید ACID باشن. اگه دو نفر همزمان یه اتاق رو رزرو کنن،
نباید هر دو موفق بشن. داده‌ها ساختاریافته‌ست (کاربر، هتل، اتاق، تاریخ، پرداخت).
نیاز به Query پیچیده (مثلاً "همه‌ی رزروهای یه کاربر تو بازه‌ی خاص") داریم.

تصمیم:
از PostgreSQL استفاده می‌کنیم.

دلیل تصمیم:
دیتابیس PostgreSQL ACID کامل داره و از تراکنش‌های پیچیده پشتیبانی می‌کنه.
هفرمت JSONB هم برای داده‌های نیمه‌ساختاریافته (مثل Metadata هتل) پشتیبانی می کنه.
حاوی Extensionهای مفید مثل PostGIS برای موقعیت مکانی است.

مزایا:
ACID کامل (جلوگیری از Double Booking)
Query پیچیده با JOIN
JSONB برای داده‌های نیمه‌ساختاریافته
Extensionهای قوی (PostGIS، TimescaleDB)

معایب:
Write Scaling محدود (نیاز به Sharding در آینده)
برای داده‌های حجیم (میلیاردها رزرو) کند می‌شه
Replication پیچیده‌ست

موارد دیگر بررسی‌شده:

الف) MongoDB:
مزایا:
Schema انعطاف‌پذیر
Sharding خودکار
معایب:
ACID کامل نداره (مگر نسخه ۴+)
برای Double Booking مناسب نیست
بدون JOIN قوی

ب) Cassandra:
مزایا:
Write سریع
مقیاس‌پذیری خطی
معایب:
Eventual Consistency
برای Double Booking فاجعه‌ست
بدون ACID

ج) MySQL:
مزایا:
ACID داره
Read سریع
معایب:
JSONB نداره
Extension محدود
Full-Text Search ضعیف

پیامدها:
مثبت: ACID، Query پیچیده، JSONB
منفی: Write Scaling محدود، Replication پیچیده
ریسک: اگه حجم داده زیاد بشه → Sharding + Citus

ADR-002: انتخاب معماری برای تراکنش توزیع‌شده (رزرو همزمان هتل و پرواز)

وضعیت: پذیرفته شده

زمینه:
کاربر می‌خواد همزمان هتل و پرواز رزرو کنه. اگه پرواز رزرو شد ولی هتل پر بود، باید پرواز کنسل بشه.
این یه تراکنش توزیع‌شده‌ست چون هتل و پرواز سرویس‌های جداگانه‌ان.

تصمیم:
از Saga Orchestration استفاده می‌کنیم.

دلیل تصمیم:
الگوی Saga Orchestration مراحل رو با یه Orchestrator مرکزی هماهنگ می‌کنه.
اگه مرحله‌ای شکست بخوره، Compensating Transaction اجرا می‌شه (مثلاً کنسل کردن پرواز).
این الگو برای تراکنش‌های توزیع‌شده استاندارده.

مزایا:
Compensating Transaction خودکار
شفافیت کامل مراحل (Audit Trail)
جداسازی منطق کسب‌وکار
مقیاس‌پذیری

معایب:
Orchestrator ممکنه Single Point of Failure بشه
پیچیدگی پیاده‌سازی
نیاز به State Machine و Persistence
Debugging سناریوهای شکست سخت
موارد دیگر بررسی‌شده:

الف) Two-Phase Commit (2PC):
مزایا:
ACID کامل
Consistency بالا
معایب:
Availability پایین
برای Microservice مناسب نیست
Blocking

ب) Saga Choreography:
مزایا:
بدون Orchestrator مرکزی
Decoupling
معایب:
پیچیدگی Tracking
Debugging سخت
بدون شفافیت کامل

ج) Best Effort:
مزایا:
سادگی
سرعت
معایب:
برای پرداخت مالی غیرقابل قبول
بدون Compensating Transaction
از دست رفتن پول
پیامدها:
مثبت: Compensating Transaction، شفافیت، Audit
منفی: پیچیدگی، Single Point of Failure
ریسک: اگه Orchestrator Down بشه → HA و State Recovery

ADR-007: انتخاب مکانیزم چندزبانگی و چندارزی

تصمیم:

دلیل تصمیم:

برای اینکه قیمت‌ها به ارز محلی کاربر نمایش داده بشن هم نرخ ارز رو از یه API (مثلاً API بانک مرکزی) می‌گیریم.
بعد نرخ‌ها رو تو Redis کش می‌کنیم تا هر بار لازم نباشه از API بخونیم.
برای تغییر direction هم از CSS dir استفاده می کنیم.
برای فارسی و عربی از dir="rtl" و برای زبان‌های چپ ‌به‌راست مثل انگلیسی از dir="ltr" استفاده می نیم

ADR-010: انتخاب مکانیزم چرخه‌ی حیات داده
وضعیت: پذیرفته شده

زمینه:
رزروها و داده‌های مالی باید ۷ سال نگه‌داری بشن (قانون مالیات).
ولی داده‌های حجیم می‌شن و کوئری کند می‌شه. از طرف دیگه GDPR حق فراموشی هم الزامی است.

تصمیم:
از Tiered Storage + Soft Delete + Anonymization استفاده می‌کنیم:
Hot (۶ ماه): PostgreSQL
Warm (۶ ماه تا ۲ سال): Elasticsearch
Cold (بیشتر از ۲ سال): S3 Glacier
GDPR: Soft Delete + Anonymize بعد از ۳۰ روز

دلیل تصمیم:
هر داده تو دیتابیسی که برای بر اساس تاریخ داده مناسب است ذخیره می‌شود.
 و Soft Delete هم Foreign Keyها رو سالم نگه می‌داره
 و Anonymize حریم خصوصی رو تضمین می‌کنه. Job شبانه انتقال‌ها رو انجام می‌ده.

مزایا:
کاهش ۷۰٪ هزینه‌ی Storage
کوئری سریع برای داده‌های اخیر
Compliance با GDPR و قانون مالیات
Foreign Keyها سالم می‌مونن

معایب:
تأخیر در بازیابی از Glacier
پیچیدگی Jobهای Archive
نیاز به Monitoring دقیق
حجم دیتابیس بیشتر (به خاطر Soft Delete)

موارد دیگر بررسی‌شده:

الف) حذف فیزیکی فوری:
مزایا:
سادگی
آزاد شدن فوری فضا
معایب:
Foreign Key می‌شکنه
GDPR ناقص (Backups)
Audit Trail از بین می‌ره

ب) نگه‌داری همه چیز در PostgreSQL:
مزایا:
سادگی
Query یکپارچه
معایب:
هزینه‌ی نجومی
کندی با حجم زیاد
Backup سنگین

ج) بدون Archive:
مزایا:
سادگی
بدون Job
معایب:
کوئری کند
هزینه‌ی بالا
نقض قانون

پیامدها:
مثبت: هزینه‌ی کم، Performance بالا، Compliance
منفی: تأخیر Restore، پیچیدگی Job
ریسک: اگه Job خطا کنه → DLQ و Retry و Alert

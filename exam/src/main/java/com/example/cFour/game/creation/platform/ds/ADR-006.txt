ADR-006: کاربردپذیری برای سازنده، بازیکن، و ادمین
وضعیت: پذیرفته شده
تاریخ: ۱۴۰۳

زمینه و مسئله
توی این پلتفرم سه جور کاربر داریم که نیازاشون زمین تا آسمون فرق داره:
سازنده کسیه که می‌خواد بازی بسازه. باید بتونه راحت Asset وارد کنه،
منطق بازی رو با Visual Scripting بچینه، بازی رو تست کنه و در نهایت منتشرش کنه.
برای این کار نیاز به یه ادیتور قوی داره که هم روی ویندوز، لینوکس و مک اجرا بشه.
بازیکن کسیه که فقط می‌خواد بازی کنه. براش مهم اینه که سریع بازی مورد علاقه‌ش رو پیدا کنه،
بدون دردسر وارد بشه و بازی روان اجرا بشه. نیازی به دیدن پیچیدگی‌های ادیتور نداره.
ادمین کسیه که باید محتوا رو مدیریت کنه. باید بتونه بازی‌های نامناسب رو حذف کنه،
به شکایت‌ها رسیدگی کنه، کاربرای متخلف رو مسدود کنه و آمار کلی پلتفرم رو ببینه.
اگه بخوایم همه اینا رو تو یه رابط کاربری واحد بریزیم، تجربه هر سه گروه خراب می‌شه. سازنده با فیلترهای اضافی گیج می‌شه،
بازیکن با ابزارهای حرفه‌ای ادیتور کاری نداره، و ادمین هم دسترسی لازم رو پیدا نمی‌کنه.

تصمیم
تصمیم ۱: Creator Studio (ادیتور اختصاصی سازنده)
توضیحات:
یه اپلیکیشن دسکتاپ جداگانه برای سازنده‌ها می‌سازیم که روی هر سه OS اجرا می‌شه.
این ادیتور شامل یه محیط گرافیکی برای چیدن صحنه، یه ویرایشگر Node-based برای منطق بازی، یه پنل مدیریت Asset،
و یه بخش برای تست و انتشار بازیه. رابط کاربری طوری طراحی می‌شه که کاربر غیرفنی هم بتونه باهاش کار کنه. مثلاً برای اضافه کردن یه دشمن،
فقط کافیه از پنل کنار صفحه یه مدل رو بکشه و بندازه تو صحنه.
مزایا:
سازنده تمام ابزارهای لازم رو یه جا داره و نیازی به جابه‌جایی بین چند برنامه نیست.
چون ادیتور دسکتاپه، می‌تونه از تمام قدرت سخت‌افزار (GPU، RAM) استفاده کنه و برای پروژه‌های سنگین مناسب‌تره.
محیط ایزوله‌ست و سازنده می‌تونه بدون نگرانی از دسترسی‌های ناخواسته، روی پروژه‌ش کار کنه.
معایب:
توسعه‌ی یه ادیتور دسکتاپ با WASM یا Electron کار سنگینیه و نیاز به تیم فنی قوی داره.
به‌روزرسانی ادیتور سخت‌تر از یه اپ وب هست و باید نسخه‌بندی دقیق انجام بشه.
اگه کاربر بخواد از چند دستگاه مختلف کار کنه، باید پروژه رو دستی Sync کنه (مگر اینکه سیستم ذخیره‌سازی ابری رو پیاده‌سازی کنیم).



تصمیم ۲: Player Client (کلاینت بازیکن)
توضیحات:
برای بازیکنا یه کلاینت سبک می‌سازیم که هم روی دسکتاپ نصب می‌شه و هم به صورت وب در دسترسه. این کلاینت فقط برای پیدا کردن و اجرای بازیه. رابط کاربری ساده‌ست: یه صفحه اصلی با بازی‌های پیشنهادی، یه بخش جستجو، و یه دکمه بزرگ برای بازی کردن. بعد از انتخاب بازی، کلاینت اون رو دانلود می‌کنه (یا استریم) و اجرا می‌کنه. هیچ ابزار ساخت و ویرایشی توش نیست.
مزایا:
بازیکن بدون هیچ پیچیدگی اضافی، فقط بازی رو انتخاب می‌کنه و بازی می‌کنه.
حجم کلاینت کمه و روی سیستم‌های ضعیف هم اجرا می‌شه.
می‌شه به راحتی روی مرورگر هم اجراش کرد (با WASM) و نیازی به نصب نداره.
معایب:
چون کلاینت سبکه، نمی‌تونه بازی‌های خیلی سنگین رو با بهترین کیفیت اجرا کنه (مگر با استریم ابری).
اگه بخوایم قابلیت ساخت بازی رو هم بهش اضافه کنیم، دوباره همون مشکل ادیتور پیش میاد.
برای بازی‌های Multiplayer، باید کلاینت با سرور بازی هماهنگ باشه و این پیچیدگی رو به کلاینت تحمیل می‌کنه.



تصمیم ۳: Admin Dashboard (پنل مدیریت)
توضیحات:
یه پنل وب جداگانه برای ادمین‌ها می‌سازیم. توی این پنل، ادمین می‌تونه لیست بازی‌های گزارش‌شده رو ببینه، محتوا رو بررسی کنه، کاربرا رو مدیریت کنه (مسدود کردن، هشدار دادن)، و آمار کلی پلتفرم رو مشاهده کنه. همچنین ابزارهایی برای بررسی شکایت‌ها، مدیریت دسته‌بندی‌ها و نظارت بر درآمد سازندگان داره. دسترسی‌ها بر اساس نقش (Admin, Moderator, Support) تعریف می‌شه.

مزایا:

ادمین می‌تونه سریع و کارا به مشکلات رسیدگی کنه (مثلاً حذف یه بازی نامناسب در چند ثانیه).
همه ابزارهای مدیریتی یه جا جمعن و نیازی به جابه‌جایی بین سیستم‌های مختلف نیست.
چون وبیه، از هر دستگاهی قابل دسترسیه و نیازی به نصب نداره.
معایب:
پیاده‌سازی این پنل زمان‌بره و نیاز به طراحی دقیق دسترسی‌ها داره.
اگه ادمین‌ها آموزش کافی نبینن، ممکنه اشتباهاتی کنن که به کاربرا آسیب بزنه.
حجم بالای داده (مثل گزارش‌ها و لاگ‌ها) می‌تونه پنل رو کند کنه اگه بهینه نشه.

تصمیم ۴: Design System مشترک و Onboarding
توضیحات:
با اینکه سه رابط کاربری جدا داریم، ولی همه از یه Design System مشترک استفاده می‌کنن. یعنی دکمه‌ها، فونت‌ها، رنگ‌ها و آیکون‌ها همه جا یکسانن. برای هر نقش هم یه Onboarding ساده طراحی می‌کنیم. مثلاً سازنده موقع اولین ورود، یه راهنمای گام‌به‌گام می‌بینه که چطور یه بازی ساده بسازه. بازیکن هم یه راهنمای کوتاه برای پیدا کردن بازی می‌بینه.

مزایا:
کاربرا بین نقش‌های مختلف حس آشنایی دارن و یادگیری سریع‌تره.
هزینه توسعه و نگهداری کمتر می‌شه چون کامپوننت‌ها مشترکن.
Onboarding خوب باعث می‌شه کاربرا سریع‌تر راه بیان و کمتر پشتیبانی بخوان.

معایب:
ایجاد و نگهداری Design System خودش یه پروژه‌ست و زمان می‌بره.
ممکنه بعضی نیازهای خاص هر نقش با Design System مشترک خوب پوشش داده نشه.
نیاز به هماهنگی مداوم بین تیم‌های مختلف (سازنده، بازیکن، ادمین) داره.


گزینه‌های بررسی‌شده
الف) یک رابط کاربری واحد برای همه نقش‌ها:
مزایا: سادگی، یه کدبیس، نگهداری راحت‌تر
معایب: تجربه هر نقش خراب می‌شه، کاربرا گیج می‌شن، امنیت پایین (چون همه به همه چیز دسترسی دارن)

ب) فقط اپ دسکتاپ برای همه نقش‌ها (حتی ادمین):
مزایا: یکپارچگی، استفاده از قدرت سخت‌افزار
معایب: ادمین باید نصب کنه، برای کارهای سبک مناسب نیست، به‌روزرسانی سخت

ج) بدون Onboarding (کاربر خودش یاد بگیره):
مزایا: سادگی پیاده‌سازی
معایب: نرخ ریزش بالا، پشتیبانی زیاد، تجربه کاربری بد

د) استفاده از پنل‌های آماده (مثل AdminLTE برای ادمین):
مزایا: سرعت اولیه
معایب: عدم تطابق با نیازهای خاص، امنیت ممکنه ضعیف باشه، سفارشی‌سازی سخت

پیامدها
چیزایی که به دست آوردیم:

هر نقش رابط کاربری مخصوص خودش رو داره و تجربه بهینه‌ای می‌گیره.

امنیت بالاتر می‌ره چون دسترسی‌ها بر اساس نقش جداسازی می‌شن.

Onboarding و Design System مشترک باعث کاهش هزینه پشتیبانی و افزایش رضایت کاربر می‌شه.

چیزایی که از دست دادیم:

هزینه توسعه سه رابط کاربری جداگانه (زمان و منابع بیشتر).

پیچیدگی نگهداری هماهنگ بین سه تیم.

نیاز به نیروی متخصص برای هر پلتفرم (دسکتاپ، وب، موبایل).

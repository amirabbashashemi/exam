ADR-002: سازگاری در ذخیره پروژه، نسخه‌بندی، و Multiplayer State Sync

وضعیت: پذیرفته شده

تاریخ: ۱۴۰۳

زمینه و مسئله
تو این پلتفرم، سازنده‌ها دارن بازی می‌سازن و هر لحظه ممکنه تغییراتشون رو ذخیره کنن.
 از طرف دیگه، بازی‌های چندنفره باید Stateشون بین بازیکنا هماهنگ بمونه. سه تا مشکل اساسی داریم:
اول، ذخیره پروژه. اگه کاربر وسط کار یه تغییر بزرگ بده و بعد پشیمون بشه،
 باید بتونه برگرده به نسخه قبل. اگه دو نفر همزمان یه پروژه رو ویرایش کنن، تغییرات نباید از بین بره.
دوم، نسخه‌بندی. کاربر باید بتونه تاریخچه تغییراتش رو ببینه و به هر نسخه‌ای برگرده. این یعنی هر تغییر باید ثبت بشه.
سوم، Multiplayer State Sync. تو بازی‌های چندنفره، هر بازیکن یه دیدی از بازی داره.
اگه این دیدها با هم هماهنگ نباشن، بازی خراب می‌شه. باید یه سرور مرکزی تصمیم بگیره و همه رو هماهنگ کنه.

تصمیم
تصمیم ۱: نسخه‌بندی با Op Log + Snapshot
توضیحات:
هر تغییر تو پروژه به صورت یه Operation ثبت می‌شه (مثل «درخت رو جابه‌جا کن»، «دشمن رو اضافه کن»).
 این Operationها تو Cassandra ذخیره می‌شن. هر ۱۰۰۰ تغییر،
  یه Snapshot کامل از پروژه گرفته می‌شه و تو S3 ذخیره می‌شه. وقتی کاربر می‌خواد به یه نسخه قدیمی برگرده،
   آخرین Snapshot قبل از اون نسخه رو می‌گیریم و Operationهای بعدش رو دونه‌دونه اعمال می‌کنیم.
مزایا:
کاربر می‌تونه به هر نسخه‌ای برگرده (حتی ۱۰۰۰ نسخه قبل)
حجم ذخیره‌سازی بهینه‌ست (Snapshot + Delta، نه کل پروژه تو هر تغییر)
Audit Trail کامل داریم (کی، کِی، چی رو تغییر داد)
معایب:
پیاده‌سازی پیچیده‌ست (باید Operationها رو تعریف کنیم و Replay کنیم)
نیاز به یه Job برای Snapshot دوره‌ای (اگه خطا کنه، Replay کند می‌شه)
برای پروژه‌های خیلی بزرگ، Replay ممکنه چند دقیقه طول بکشه


تصمیم ۲: Multiplayer State Sync با Server-Authoritative + Client Prediction
توضیحات:
یه سرور مرکزی (Game Server) صاحب State بازیه. کلاینت‌ها فقط ورودی می‌فرستن (مثل «شلیک کن»، «برو جلو»).
 سرور پردازش می‌کنه، State جدید رو به همه می‌فرسته. برای اینکه بازی Lag نداشته باشه،
  کلاینت‌ها Client-side Prediction دارن (یعنی خودشون حدس می‌زنن نتیجه چی می‌شه) و اگه با سرور اختلاف شد،
   Rollback می‌کنن و دوباره اعمال می‌کنن.
مزایا:
تقلب خیلی سخت می‌شه (چون سرور تصمیم‌گیرنده‌ست)
تجربه روان برای بازیکن (Prediction باعث می‌شه بازی فوری به نظر برسه)
سازگار با انواع بازی (FPS، RTS، Racing)
معایب:
پیاده‌سازی پیچیده (نیاز به Prediction، Rollback، Reconciliation)
نیاز به سرور قدرتمند (CPU و Bandwidth بالا)
برای بازیکن‌های دور (Latency بالا)، Prediction سخت‌تر می‌شه


تصمیم ۳: ذخیره اتمیک با Optimistic Locking
توضیحات:
هر پروژه یه فیلد version داره. وقتی کاربر ذخیره می‌کنه، سرور چک می‌کنه که version کاربر با version دیتابیس یکی هست یا نه.
 اگه یکی بود، ذخیره می‌شه و version یکی زیاد می‌شه. اگه نبود، یعنی یکی دیگه همزمان تغییر داده و کاربر باید Merge کنه.

مزایا:
جلوگیری از از دست رفتن تغییرات (Conflict تشخیص داده می‌شه)
سادگی نسبی (نیازی به Lock طولانی نیست)
مناسب برای تک‌کاربری یا تغییرات کم
معایب:
در Conflict، کاربر باید دستی Merge کنه (تجربه کاربری خوبی نیست)
برای همکاری همزمان (چند نفر روی یه پروژه) مناسب نیست
نیاز به UI برای Merge داره (که خودش کار زیادی می‌بره)

گزینه‌های بررسی‌شده
الف) CRDT برای پروژه:
مزایا: همکاری همزمان بدون Conflict، Offline Support
معایب: پیچیدگی زیاد، برای پروژه‌های بزرگ کند می‌شه، نیاز به کتابخانه‌های سنگین

ب) Lockstep برای Multiplayer:
مزایا: سادگی، Deterministic
معایب: فقط برای بازی‌های نوبتی یا کم‌تحرک مناسبه، به Latency حساسه

ج) P2P برای Multiplayer:
مزایا: هزینه کم برای پلتفرم، بدون سرور مرکزی
معایب: NAT Traversal سخت، تقلب راحت، تجربه کاربری ضعیف

د) ذخیره کل پروژه در هر تغییر (بدون Op Log):
مزایا: سادگی
معایب: حجم نجومی، کندی، هزینه بالا

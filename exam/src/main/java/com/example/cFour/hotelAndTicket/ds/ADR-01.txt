نقاط قوت:

مشکل را درست شناسایی کردی (Stateful بودن جستجوی پرواز + تغییر لحظه‌ای قیمت)

دو گزینه را مقایسه کردی

نقاط ضعف:

تصمیم مبهم است: "ایجاد یک جاب برای استعلام دوره‌ای" — چه جابی؟ هر چند وقت؟ با چه تکنولوژی؟

نگفتی اگر بین دو اجرای Job قیمت تغییر کند، کاربر چه می‌بیند؟

Redis را گفتی ولی TTL، eviction policy، و ساختار داده را نگفتی

CQRS را اصلاً اشاره نکردی

Trade-off "قیمت ممکن است قدیمی باشد" را ننوشتی

نسخه نمره‌فول (۱۰/۱۰):


### ADR-001: استراتژی کش ترکیبی (Hybrid Caching) برای قیمت هتل و پرواز

مساله:
جستجوی پرواز Stateful است و قیمت‌ها هر دقیقه تغییر می‌کنند. هر درخواست مستقیم به GDS
(Amadeus/Sabre) هزینه‌ی مالی و latency بالا (۲-۵ ثانیه) دارد. اما کش کردن طولانی‌مدت
باعث نمایش قیمت اشتباه به کاربر و نارضایتی می‌شود.

تصمیم:
معماری کش دو‌لایه (Two-Tier Caching) بر اساس نوع داده:

۱. **هتل (قیمت پایدارتر):**
   - TTL = ۱ ساعت در Redis Cluster
   - ساختار: `hotel:{city}:{checkin}:{checkout}` → Hash
   - Cache Warming شبانه برای ۱۰۰ شهر پرطرفدار

۲. **پرواز (قیمت لحظه‌ای):**
   - TTL = ۹۰ ثانیه (Near Real-Time)
   - **Prefetch Job** هر ۶۰ ثانیه برای مسیرهای پرتقاضا (تهران-استانبول)
   - **Cache-Aside + Write-Through**: هنگام مشاهده جزئیات، قیمت از GDS تأیید می‌شود
   - در لحظه‌ی پرداخت: **Final Price Verification** با GDS (الزامی)

۳. **CQRS**:
   - Write: PostgreSQL (رزرو نهایی)
   - Read: Redis + Elasticsearch (جستجو)

گزینه‌های جایگزینِ بررسی‌شده:
- *استعلام با هر درخواست*: رد شد چون هزینه GDS (۰.۰۱$ به ازای هر درخواست) در مقیاس میلیونی غیرقابل تحمل است.
- *بدون کش (Real-time)*: رد شد چون latency ۵ ثانیه برای UX غیرقابل قبول است.
- *کش ۱ ساعته برای پرواز*: رد شد چون نرخ تبدیل (Conversion) به شدت کاهش می‌یابد.

پیامدها:
- مثبت: کاهش ۸۰٪ هزینه GDS، latency < ۲۰۰ms برای ۹۵٪ درخواست‌ها
- منفی: پیچیدگی مدیریت TTL و نیاز به monitoring برای cache hit ratio
- نیاز به **Circuit Breaker** برای GDS (اگر GDS down شد، از آخرین کش استفاده شود)

**Related C4 Level:** Container Level 2 (Search Service + Redis + GDS Adapter)

ADR-003: Settings Service + Rule Engine + Cross-Device Sync
وضعیت: پذیرفته شده

زمینه و مسئله
تو یه پیامرسان با ۱۰۰ میلیون کاربر، هر کاربر باید بتونه تنظیمات شخصیش رو بدون کدنویسی و بلادرنگ تغییر بده. این تنظیمات شامل Privacy (Last Seen، Profile Photo، Read Receipts)، Notification (Mute، DND)، Block/Unblock، Group Settings، و Business Settings (برای WhatsApp Business) میشه.

چند تا چالش داریم: تنظیمات باید بلادرنگ تو همه دستگاههای کاربر Sync بشن. Privacy باید تو سرور اعمال بشه، نه کلاینت، وگرنه قابل دور زدنه. قوانین شرطی مثل «اعلانها رو بین ۱۱ شب تا ۷ صبح خاموش کن» نیاز به Rule Engine دارن. Block باید فوری اعمال بشه (زیر ۱ ثانیه). و حجم تنظیمات زیاده: ۱۰۰ میلیون کاربر × ۵۰ تنظیم = ۵ میلیارد رکورد.

تصمیم
۱. Settings Service (میکروسرویس مستقل)
یه سرویس جداگانه برای همه تنظیمات کاربر. دیتابیس PostgreSQL برای دادههای ساختاریافته و JSONB برای تنظیمات پویا. جدول اصلی user_settings با فیلدهای privacy، notifications، blocked_users، group_defaults، business_settings و یه فیلد version برای Optimistic Locking.
مزایا:
جداسازی منطق تنظیمات از بقیه سرویسها
JSONB برای انعطافپذیری تنظیمات پویا
مقیاسپذیری با Sharding بر اساس userId

معایب:
یه سرویس بیشتر برای نگهداری
تأخیر شبکه بین سرویسها
نیاز به Cache برای Performance

۲. Rule Engine (Drools) برای قوانین شرطی
قوانین تو PostgreSQL (JSONB) ذخیره میشن. Drools قوانین رو تو Runtime اعمال میکنه. مثلاً «اگه کاربر در حال تایپه، Typing Indicator نشون بده» یا «اگه فرستنده تو Block Listه، پیام رو Drop کن». Cache تو Redis با TTL ۵ دقیقه.
مزایا:
پویایی کامل بدون نسخهگذاری
قوانین پیچیده If-Then قابل تعریف
استقلال کاربر از تیم فنی
معایب:
پیچیدگی Drools و نیاز به یادگیری
ریسک قانون اشتباه
Single Point of Failure اگه Rule Engine بخوابه

۳. Cross-Device Sync
کاربر ممکنه سه دستگاه داشته باشه (موبایل، تبلت، لپتاپ). وقتی تنظیمات رو تو یه دستگاه تغییر میده، Settings Service تو PostgreSQL ذخیره میکنه و یه Kafka Event settings-changed میفرسته. WebSocket Gateway اون رو به همه دستگاههای کاربر Push میکنه.
هر تغییر یه version جدید میگیره. اگه کلاینت version قدیمی داشت، سرور Full Sync میفرسته. Conflict Resolution با Last-Write-Wins و Version Check.
مزایا:
تنظیمات بلادرنگ تو همه دستگاهها
Conflict Resolution خودکار
Reconnection سریع با Delta Sync
معایب:
تأخیر حدود ۱۰۰ میلیثانیه تو Sync
نیاز به WebSocket Gateway
پیچیدگی Version Management

۴. Privacy Enforcement تو سرور (نه کلاینت)
تنظیمات Privacy فقط تو سرور اعمال میشن تا قابل دور زدن نباشن. مثلاً برای Block، سرور چک میکنه آیا فرستنده تو Block List گیرنده هست یا نه. Block List تو Redis Cache با TTL ۱ ساعته.
مزایا:
غیرقابل دور زدن توسط کلاینت
امنیت بالا
Sync بین دستگاهها
معایب:
Load روی سرور
نیاز به Cache برای Performance
تأخیر تو اعمال تغییرات


۵. Block/Unblock فوری و اتمیک
کاربر A درخواست Block کاربر B رو میده. Settings Service تو PostgreSQL ذخیره میکنه و Redis Cache رو آپدیت میکنه. یه Kafka Event user-blocked میره. Message Service قبل از ذخیره هر پیام، Block List رو چک میکنه. Unblock هم مشابهه، فقط Cache Invalidate میشه.
مزایا:
اعمال فوری (زیر ۱ ثانیه)
اتمیک با Redis Set
Audit Trail کامل
معایب:
نیاز به Redis Cluster با HA
حجم Redis رشد میکنه
پیچیدگی Cache Invalidation

۶. Group Settings با نقشهای Admin/Member
هر گروه تنظیمات مخصوص خودش رو داره: کی میتونه پیام بفرسته، کی میتونه اطلاعات گروه رو ویرایش کنه، کی میتونه عضو اضافه کنه، و تأیید عضویت جدید برای گروههای بزرگ. نقشها: Creator، Admin، Member. Cache تو Redis با TTL ۵ دقیقه.
مزایا:
کنترل کامل Admin بر گروه
انعطافپذیری تو تنظیمات
مقیاسپذیری برای گروههای بزرگ
معایب:
پیچیدگی مدیریت نقشها
نیاز به Cache برای Performance
Conflict Resolution تو گروههای بزرگ

۷. WhatsApp Business Settings
برای کاربران تجاری: Business Hours، Auto-reply، Catalog Management، Away Messages. یه REST API جداگانه با API Key و Webhook برای Incoming Messages.
مزایا:
API جداگانه برای Enterprise
Auto-reply و Catalog
Webhook برای Integration
معایب:
پیچیدگی API Management
هزینه نگهداری
نیاز به مستندات کامل

۸. Redis Cache برای Performance
چند لایه Cache داریم: settings:{userId} (TTL ۵ دقیقه)، privacy:{userId} (TTL ۵ دقیقه)، blocked:{userId} (TTL ۱ ساعت)، group:{groupId}:settings (TTL ۵ دقیقه). هنگام تغییر، Kafka Event میره و Cache Invalidate میشه. هنگام Login، تنظیمات از DB به Redis Load میشه.
مزایا:
سرعت بالا (In-Memory)
کاهش Load روی PostgreSQL
مقیاسپذیری
معایب:
هزینه RAM (۱۰۰ میلیون کاربر × ۱KB = ۱۰۰GB)
پیچیدگی Cache Invalidation
Single Point of Failure

گزینههای بررسیشده
الف) تنظیمات فقط تو کلاینت: سادهست ولی Privacy قابل دور زدنه. Sync بین دستگاهها ممکن نیست. اگه کاربر اپ رو Reinstall کنه، تنظیمات میپره. رد شد.
ب) Config Server (Spring Cloud Config): Centralized و Git-based ولی برای Business User قابل استفاده نیست. فقط Key-Value داره. نیاز به Restart. برای ۱۰۰ میلیون کاربر مقیاس نمیگیره. رد شد.
ج) Feature Toggle (LaunchDarkly): Real-time و UI داره ولی فقط Boolean (روشن/خاموش). برای قوانین شرطی مناسب نیست. هزینه بالا. رد شد.
د) Cassandra به جای PostgreSQL: مقیاسپذیری افقی و Write Performance بالا ولی Query پیچیده سخته. Transaction نداره. برای JSONB مناسب نیست. رد شد.
ه) Block List تو کلاینت: سرعت بالا و بدون Load روی سرور ولی قابل دور زدنه. Sync ممکن نیست. اگه Block List بزرگ باشه، کلاینت کند میشه. رد شد.

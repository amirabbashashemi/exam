ADR-002: ترتیب پیامها، Read Receipt، و Fan-out گروهی
وضعیت: پذیرفته شده

زمینه و مسئله
تو یه پیامرسان با ۱۰ میلیارد پیام در روز و ۱۰۰ میلیون کاربر، سه تا مشکل جدی داریم:
اول، ترتیب پیامها. دو نفر همزمان پیام میفرستن، کدوم اوله؟ ساعت گوشی هر کاربر فرق داره و پیامها ممکنه با تأخیر شبکه، پس و پیش برسن.
دوم، Read Receipt. تو گروه ۱۰۰ هزار نفری، اگه هر عضو یه Read Receipt بفرسته، یعنی ۱۰۰ هزار رکورد برای یه پیام! باید بین دقت و مقیاسپذیری تعادل برقرار کنیم.
سوم، Fan-out گروهی. همون گروه ۱۰۰ هزار نفری، اگه هر پیام به همه Push بشه، یعنی ۱۰۰ هزار ارسال برای یه پیام. ده پیام در دقیقه که بفرستن، میشه ۱ میلیون ارسال در دقیقه. کافکا میترکه و پهنای باند به فنا میره.

تصمیم
۱. Lamport Timestamp برای ترتیب پیامها
هر پیام سه تا فیلد داره: lamportClock، sequence، و serverTimestamp. لامپورت یه عدد منطقیه که با هر رویداد زیاد میشه (نه ساعت واقعی). سکوئنس هم از Redis با Atomic Increment گرفته میشه. کلاینت پیامها رو بر اساس این دوتا میچینه.
چرا لامپورت و نه Unix Timestamp؟ چون یونیکس وابسته به ساعت سروره و بین سرورها اختلاف داره. لامپورت مستقل از ساعت واقعیه و یه ترتیب کلی میسازه.
مزایا:
ترتیب دقیق مستقل از ساعت واقعی، بدون مشکل Clock Skew
مقیاسپذیری خطی با Redis Atomic Increment
یه ترتیب یکسان تو همه کلاینتها
معایب:
مدیریت Clock تو کلاینت و سرور پیچیدهتره
برای Causality دقیق کافی نیست (نیاز به Vector Clock)
اگه Redis بخوابه، تولید Sequence متوقف میشه

۲. Read Receipt با Batch و Aggregation
سه حالت داریم. تو چت خصوصی، هر کاربر فقط lastReadMessageId رو ذخیره میکنه و Read Receipt فوری Push میشه. تو گروه کوچیک (زیر ۱۰۰ نفر)، هر عضو lastReadMessageId رو تو Cassandra ذخیره میکنه و یه Count تجمعی تو Redis داریم. تو گروه بزرگ (بالای ۱۰۰ نفر)، هر ۵ ثانیه یه Batch Update میزنیم و فقط تعداد کل خوانندهها رو نگه میداریم (با HyperLogLog). یعنی «۵۰ هزار نفر خواندهاند» به جای لیست تک تک افراد.
مزایا:
مقیاسپذیری بالا، Load ثابت حتی تو گروههای بزرگ
تأخیر کم تو چت خصوصی (زیر ۱۰۰ میلیثانیه)
کاهش شدید نوشتن تو Cassandra (از ۱۰۰ هزار در ثانیه به ۲۰)
معایب:
دقت تو گروه بزرگ کمتره (تقریبی)
تأخیر تا ۵ ثانیه تو گروه بزرگ
نیاز به مدیریت State تو Consumer

۳. Hybrid Fan-out
یه آستانه ۱۰۰ نفره داریم که تو Config Server قابل تنظیمه. گروه زیر ۱۰۰ نفر: Fan-out on Write. یعنی پیام تو Cassandra ذخیره میشه و Kafka Event به تاپیک fanout-small-group میره و Consumer فوراً به همه Push میکنه. گروه بالای ۱۰۰ نفر: Fan-out on Read. یعنی پیام فقط ذخیره میشه و کاربر وقتی چت رو باز میکنه، پیامهای جدید رو Pull میکنه.
مزایا:
تأخیر کم برای گروههای کوچیک
صفر Push برای گروه ۱۰۰ هزار نفری
Load ثابت و قابل پیشبینی
معایب:
تأخیر بیشتر برای اعضای آنلاین تو گروه بزرگ (تا ۵ ثانیه)
پیچیدگی منطق تشخیص اندازه گروه
نیاز به Cache برای اندازه گروه

۴. Kafka برای Consistency
تاپیک messages با پارتیشن بر اساس conversationId. اینطوری ترتیب پیامها تو یه گفتگو تضمین میشه. Producer با acks=all و Consumer با Idempotent Processing. تاپیک read-receipts هم برای Batch Processing داریم که هر ۵ ثانیه یه بار تو Cassandra مینویسه.
مزایا:
تضمین ترتیب تو هر Conversation
Exactly-Once با acks=all
Replay برای Recovery
معایب:
Single Point of Failure اگه Kafka بخوابه
نیاز به نگهداری و Monitoring
تأخیر تو Batch Processing

۵. Idempotency برای جلوگیری از تکرار
هر پیام یه clientMessageId یکتا داره (UUID از کلاینت). سرور چک میکنه اگه قبلاً پردازش شده، نادیده بگیره. تو Redis با SETNX و TTL ۲۴ ساعته ذخیره میشه.
مزایا:
جلوگیری از پیام تکراری تو Retry شبکه
سادگی پیادهسازی با Redis
کاهش بار روی Cassandra
معایب:
وابستگی به Redis (اگه بخوابه، Idempotency از دست میره)
حجم Redis رشد میکنه (نیاز به Cleanup)
کلاینت باید UUID تولید کنه
گزینههای بررسیشده
الف) Unix Timestamp (نانوثانیه): سادهست ولی Clock Skew بین سرورها داره. تو ترافیک بالا ممکنه دو پیام همون نانوثانیه رو بگیرن. رد شد.
ب) زمان کامپیوتر کاربر: خیلی سادهست ولی کاربر میتونه ساعت گوشیش رو عوض کنه. غیرقابل اعتماد. رد شد.
ج) Vector Clock: Causality رو دقیق تشخیص میده ولی برای گروه ۱۰۰ هزار نفری، بردار ۱۰۰ هزار عنصری میشه. Overkill. رد شد.
د) Fan-out on Write برای همه گروهها: تأخیر کم ولی برای گروه بزرگ، ۱۰۰ هزار Push برای یه پیام. غیرقابل تحمل. رد شد.
ه) Fan-out on Read برای همه گروهها: Load کم ولی برای گروه دو نفره، تأخیر اضافه. تجربه کاربری ضعیف. رد شد.
و) Read Receipt بدون Batch: دقت کامل ولی ۱۰۰ هزار Read Receipt برای یه پیام. شبکه اشباع میشه. رد شد.

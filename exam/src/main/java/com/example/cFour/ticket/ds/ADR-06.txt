سوال پرسیده بود: "کاربردپذیری و سهولت استفاده برای کاربران با حداقل نیاز به آموزش"

این یعنی چیزهایی مثل:

Onboarding Wizard

Progressive Disclosure

Real-time Validation

Error Recovery

RTL/LTR Support

Accessibility

شما به جای اینها، درباره‌ی معماری جستجو (ELK vs DB) نوشتید. این یک اشتباه استراتژیک است که ۸ نمره از دست می‌دهد.

نسخه نمره‌فول (۱۰/۱۰):
### ADR-006: کاربردپذیری و تجربه کاربری (UX) برای کاربران غیرفنی

Context:
کاربران نهایی (غیرفنی) باید بتوانند در کمتر از ۲ دقیقه هتل و پرواز رزرو کنند.
آمار نشان می‌دهد ۶۰٪ کاربران در مرحله پرداخت رها می‌کنند.

Decision:

۱. Onboarding Wizard ۳ مرحله‌ای:
   - مرحله ۱: انتخاب مقصد + تاریخ (با تقویم قیمت‌ها)
   - مرحله ۲: انتخاب هتل/پرواز از نتایج
   - مرحله ۳: پرداخت
   - Progress Indicator + Skip Option

۲. Progressive Disclosure:
   - صفحه اول: فقط ۳ فیلتر اصلی (مقصد، تاریخ، تعداد نفرات)
   - فیلترهای پیشرفته (کلاس پروازی، امکانات هتل) در Accordion
   - Tooltip ساده: به جای "Rate Limit" بگو "تعداد درخواست"

۳. Smart Defaults:
   - بر اساس IP: ارز و زبان پیش‌فرض
   - بر اساس تاریخ: پیشنهاد بهترین زمان سفر
   - بر اساس رفتار: پیشنهاد هتل مشابه

۴. Real-time Validation:
   - اعتبارسنجی لحظه‌ای شماره کارت، ایمیل، تاریخ
   - پیام خطای مفید: "شماره کارت باید ۱۶ رقم باشد"

۵. Auto-save Draft:
   - ذخیره خودکار فرم در Redis (TTL=۲۴h)
   - اگر کاربر صفحه را بست، در بازگشت اطلاعات بازیابی می‌شود

۶. Error Recovery:
   - Retry با یک کلیک (با Idempotency Key)
   - پیشنهاد راه‌حل: "پرداخت ناموفق. کارت دیگری امتحان کنید؟"

۷. RTL/LTR + Accessibility:
   - CSS `dir="rtl"` برای فارسی/عربی
   - ARIA Labels برای Screen Reader
   - کنتراست بالا + فونت بزرگ‌تر

Alternatives Considered:
- فرم طولانی تک‌صفحه‌ای: رد شد چون نرخ تکمیل را ۴۰٪ کاهش می‌دهد.
- بدون Auto-save: رد شد چون کاربر باید از اول شروع کند.

Consequences:
- مثبت: نرخ تکمیل رزرو از ۴۰٪ به ۷۵٪ افزایش می‌یابد
- منفی: پیچیدگی Frontend، نیاز به A/B Testing
- نیاز به Analytics برای ردیابی رفتار کاربر

Related C4 Level: Component Level 3 (Frontend Wizard + Validation Service)

ADR-001: WebSocket + Sharding + Connection Registry
وضعیت: پذیرفته شده
تاریخ: ۱۴۰۴/۰۷/۱۰
تصمیم‌گیرنده: تیم معماری

زمینه
قراره پیام‌رسانمون ۱۰۰ میلیون کاربر همزمان رو با تأخیر زیر ۵۰۰ میلی‌ثانیه سرویس بده. روزی ۱۰ میلیارد پیام رد و بدل می‌شه. سه تا نکته هم هست که نمی‌ذاره راحت بخوابیم:
کاربرا می‌خوان ببینن کی آنلاینه و کی داره تایپ می‌کنه.
تو گروه‌های تا ۱۰۰ هزار نفری، یه پیام باید به همه برسه.
کسی که آفلاین بوده، وقتی برگشت باید پیامای از دست رفته رو بگیره.
راه REST جواب نمی‌ده چون Stateless هست و برای Connection پایدار ساخته نشده. از اون طرف اگه بخوایم تو گروه بزرگ برای هر پیام به همه Push بزنیم، عملاً Kafka رو منفجر کردیم.

تصمیم
ترکیبی از WebSocket، Sharding، Connection Registry، Hybrid Fan-out و Kafka رو انتخاب کردیم.

۱. WebSocket Gateway
به جای REST، از WebSocket استفاده می‌کنیم تا یه ارتباط Persistent بین Client و سرور باشه.
هر سرور با Netty (که Non-blocking هست) می‌تونه تا ۱ میلیون Connection رو نگه داره.
با ۱۰۰ تا سرور، به ۱۰۰ میلیون Connection می‌رسیم.
مزیتش اینه که سرور خودش می‌تونه Push کنه، بدون اینکه Client مدام Poll بزنه.
از WSS استفاده می‌کنیم که رمزنگاری‌شده‌ست.

۲. Connection Registry
تو Redis نگه می‌داریم که هر کاربر به کدوم سرور وصله:
SET user:{userId}:server {serverId} EX 60
وقتی می‌خوایم پیامی به کاربر بدیم، اول از Redis می‌پرسیم کجاست.
اگه آفلاین بود، پیام تو Kafka می‌مونه تا وقتی برگرده.
برای Presence (آنلاین/آفلاین/آخرین بازدید) هم از Pub/Sub خود Redis استفاده می‌کنیم.


۳. Sharding بر اساس userId
هر کاربر همیشه به یه سرور مشخص وصل می‌شه:
text
serverId = hash(userId) % 100
از Consistent Hashing استفاده می‌کنیم که وقتی سرور اضافه یا کم می‌شه، همه‌چیز به هم نریزه. HAProxy با Sticky Session مسیریابی رو انجام می‌ده.


۴. Kafka برای تحویل Async
یه تاپیک messages داریم که بر اساس conversationId پارتیشن‌بندی شده تا ترتیب پیامای یه چت حفظ بشه.
Producer سرویس Message هست و Consumer خود WebSocket Gateway. برای Presence یه تاپیک جدا گذاشتیم.


۵. Hybrid Fan-out
اینجا مهم‌ترین تصمیمه. دو تا حالت داریم:
گروه کمتر از ۱۰۰ نفر: Fan-out on Write. یعنی پیام میاد، همون لحظه به همه Push می‌شه. تأخیر کمه و Load قابل قبوله.
گروه بیشتر از ۱۰۰ نفر: Fan-out on Read. پیام فقط یه بار ذخیره می‌شه و کاربر وقتی چت رو باز می‌کنه،
خودش Pull می‌کنه. اگه گروه ۱۰۰ هزار نفره باشه و بخوایم Write کنیم، برای هر پیام ۱۰۰ هزار ارسال داریم که اصلاً منطقی نیست.
آستانه‌ی ۱۰۰ از Config Server قابل تغییره.

۶. Reconnection
یکClient هنگام قطعی یه Resume Token می‌گیره. وقتی برگشت، آخرین messageId رو می‌فرسته و سرور پیامای از دست رفته رو از Kafka یا Cassandra می‌خونه.
برای Reconnect از Exponential Backoff (۱، ۲، ۴، ۸، ۱۶ ثانیه) استفاده می‌کنیم.

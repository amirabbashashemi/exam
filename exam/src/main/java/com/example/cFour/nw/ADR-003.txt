ADR-003: الگوهای Resilience (Circuit Breaker + Retry + Bulkhead)
وضعیت: پذیرفته شده

زمینه:
موتور پیشنهاددهنده به سرویس‌های خارجی (مثل Analytics، ML Model) وابسته است. اگه یکی از این سرویس‌ها کند یا خراب بشه، درخواست‌ها صف می‌شن و کل سیستم از کار می‌افته (Cascading Failure).

تصمیم:
استفاده از Resilience4j با ترکیب سه الگو:

Circuit Breaker: قطع ارتباط بعد از ۵۰٪ خطا در ۱۰ ثانیه

Retry: ۳ بار با Exponential Backoff (۱s, ۲s, ۴s)

Bulkhead: Thread Pool جداگانه برای هر سرویس خارجی

دلیل تصمیم:
Circuit Breaker جلوی Cascading Failure رو می‌گیره. Retry خطاهای موقت رو جبران می‌کنه. Bulkhead تضمین می‌کنه که یه سرویس کند، Thread Pool بقیه سرویس‌ها رو اشباع نکنه.

مزایا:

جلوگیری از Cascading Failure

بازیابی خودکار (بعد از رفع مشکل، مدار بسته می‌شه)

جداسازی منابع (یه سرویس خراب، بقیه رو خراب نمی‌کنه)

معایب:

تنظیم آستانه‌ها نیاز به تست و تجربه داره

Retry ممکنه سرویس مقصد رو Overload کنه

پیچیدگی Debugging (کدوم مرحله شکست خورد؟)

موارد دیگر بررسی شده:

الف) Retry ساده (بدون Circuit Breaker):
مزایا:

سادگی پیاده‌سازی

پوشش خطاهای موقت
معایب:

Retry Storm (اگه سرویس خراب باشه، بار بیشتر می‌شه)

Cascading Failure

بدون Fallback

ب) Timeout فقط:
مزایا:

سادگی

جلوگیری از انتظار بی‌نهایت
معایب:

کافی نیست (سرویس ممکنه کند بمونه ولی Down نشه)

Thread Pool اشباع می‌شه

ج) Bulkhead به تنهایی:
مزایا:

جداسازی منابع

جلوگیری از Exhaustion
معایب:

بدون قطع ارتباط با سرویس خراب

Retry نداره

پیامدها:

مثبت: مقاومت بالا در برابر خرابی، Fail Fast

منفی: پیچیدگی تنظیمات، نیاز به Monitoring دقیق

ریسک: آستانه اشتباه → Alert + بازبینی دوره‌ای

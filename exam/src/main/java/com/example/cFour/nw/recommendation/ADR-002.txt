ADR-002: استراتژی Caching برای مقابله با بار سنگین
وضعیت: پذیرفته شده

زمینه:
موتور پیشنهاددهنده باید برای میلیون‌ها کاربر، پیشنهاد شخصی‌سازی‌شده تولید کنه. اگه هر درخواست مستقیم به دیتابیس بره، زیر بار سنگین می‌شکنه.

تصمیم:
استفاده از Redis Cluster با استراتژی Cache-Aside و TTL مبتنی بر نوع داده:

پیشنهادات پرتکرار: TTL = ۵ دقیقه

پروفایل کاربر: TTL = ۳۰ دقیقه

Trendها: TTL = ۱ دقیقه

دلیل تصمیم:
Redis In-Memory هست و سرعتش زیر ۱ms. با Cache-Aside، فقط در صورت Cache Miss به دیتابیس می‌ریم. اینطوری ۹۰٪ درخواست‌ها از کش پاسخ می‌گیرن و بار دیتابیس ۱۰ برابر کاهش پیدا می‌کنه.

مزایا:
کاهش ۹۰٪ بار روی دیتابیس
Latency < ۵ms برای ۹۰٪ درخواست‌ها
مقیاس‌پذیری افقی با Redis Cluster
معایب:
Single Point of Failure (اگه Redis Cluster Down بشه)
مصرف RAM زیاد (هزینه)
Cache Invalidation پیچیده (کی داده رو Update کنیم؟)

موارد دیگر بررسی شده:
الف) بدون Cache (مستقیم به DB):
مزایا:
همیشه داده تازه (Consistency کامل)
سادگی پیاده‌سازی
معایب:
کندی زیر بار سنگین
دیتابیس به سرعت اشباع می‌شه
هزینه دیتابیس بالا

ب) Local Cache (In-Memory در هر سرویس):
مزایا:
سرعت فوق‌العاده (بدون Network)
بدون وابستگی به Redis
معایب:
محدودیت حافظه هر سرویس
ناهماهنگی بین Instanceها
Cache Invalidation سخت


ج) Memcached:
مزایا:
سادگی، سرعت بالا
Multi-threaded
معایب:
فقط Key-Value (بدون ساختار داده پیشرفته)
بدون Persistence
بدون Replication داخلی


پیامدها:
مثبت: بار دیتابیس ۱۰ برابر کمتر، Latency پایین
منفی: هزینه Redis Cluster، پیچیدگی Invalidation
ریسک: Redis Down → Fallback به دیتابیس + Rate Limiting

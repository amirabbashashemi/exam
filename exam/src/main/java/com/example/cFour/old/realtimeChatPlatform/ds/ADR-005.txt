ADR-005: مدیریت چرخه حیات داده‌ها
وضعیت: پذیرفته شده
تاریخ: ۱۴۰۳
تصمیم‌گیرنده: تیم معماری

زمینه
روزانه حدود ۱۰ میلیارد پیام رد و بدل می‌شه و سرور Media هم روزی ۵۰۰ ترابایت داده جدید می‌گیره. اگه همه اینا رو بخوایم تو یه جا نگه داریم، هم هزینه‌مون سر به فلک می‌کشه، هم کوئری‌ها کند می‌شن. از اون طرف، GDPR هم حق فراموشی رو الزام کرده و نمی‌تونیم هرچی خواستیم نگه داریم. یه مسئله دیگه هم اینه که کاربرا PIN دارن و انتظار دارن اگه گوشیشون رو عوض کردن، بتونن بکاپشون رو برگردونن.
خلاصه، سه تا مشکل داریم: حجم، هزینه، و قانون.

تصمیم
۱. لایه‌بندی پیام‌ها بر اساس سن
پیام‌ها رو تو سه لایه نگه می‌داریم:
تا ۳ ماه تو Cassandra (چون سریع‌ترین دسترسی رو داره و پیامای جدیدترین بیشترین استفاده رو دارن)
۳ ماه تا ۲ سال تو S3 Infrequent Access (ارزون‌تره، دسترسی بهش کمه ولی غیرمعمول نیست)
بیشتر از ۲ سال تو S3 Glacier (فقط برای Audit و شکایت‌های قانونی)
بیشتر از ۷ سال کلاً حذف می‌شه (چون قانوناً دیگه نیازی نیست)
یه Job شبانه این کار رو انجام می‌ده و انتقال‌ها رو Kafka Event می‌زنه.

۲. حذف پیام‌ها
وقتی کاربر پیامی رو حذف می‌کنه، اول Soft Delete می‌شه (is_deleted = true). بعد از ۳۰ روز، یه Job میاد و کاملاً از Cassandra پاکش می‌کنه. Media مربوط به اون پیام هم از S3 حذف می‌شه.
چرا Soft Delete؟ چون اگه کاربر تا ۳۰ روز بعد پشیمون شد، بتونه برگردونه. بعد از اون دیگه غیرقابل برگشته.


۳. GDPR و حق فراموشی
این بخش حساس‌ترین قسمته. سه تا کار باید انجام بشه:
اول، Soft Delete فوری. کاربر درخواست می‌ده، همون لحظه داده‌هاش از دید بقیه مخفی می‌شه.
دوم، بعد از ۳۰ روز، Metadata رو Anonymize می‌کنیم (اسم و ایمیل رو با یه شناسه تصادفی جایگزین می‌کنیم).
سوم، و از همه مهم‌تر، کلیدهای رمزنگاری کاربر رو حذف می‌کنیم. این برای E2EE حیاتیه. حتی اگه یه نسخه از پیام‌ها تو بکاپ مونده باشه، چون کلیدش نیست، قابل خوندن نمی‌شه. این تکنیک به Crypto-Shredding معروفه.


۴. بکاپ E2EE
کاربر تو تنظیمات یه PIN انتخاب می‌کنه. کلیدهای رمزنگاریش با Argon2 (از PIN) هش می‌شن و بکاپ رمزنگاری‌شده تو S3 ذخیره می‌شه. وقتی کاربر گوشیش رو عوض کرد، PIN رو وارد می‌کنه و بکاپش برمی‌گرده.
نکته‌ای که اینجا هست: اگه PIN رو فراموش کنه، دیگه هیچ راهی برای بازیابی نیست. این یه Trade-off آگاهانه‌ست — امنیت بیشتر به قیمت ریسک گم شدن داده.


۵. آرشیو Media
Media یه چرخه جداگانه داره چون حجمش خیلی بیشتره:
تا ۱ ماه تو S3 Standard
۱ ماه تا ۱ سال تو S3 Infrequent Access
بیشتر از ۱ سال تو S3 Glacier

۶. بازیابی از آرشیو
اگه کاربر درخواست بازیابی داد، درخواستش می‌ره تو Kafka. یه Job برمی‌داره و از Glacier می‌خونه (معمولاً ۳ تا ۵ ساعت طول می‌کشه). بعدش به کاربر اطلاع می‌دیم.
گزینه‌های دیگه‌ای که بررسی کردیم
حذف فیزیکی فوری: ساده‌ست ولی Foreign Keyها می‌شن و GDPR رو کامل پوشش نمی‌ده.
بدون بکاپ E2EE: کاربر با تعویض گوشی همه چیز رو از دست می‌ده. غیرقابل قبول.
همه چیز تو S3 Standard: هزینه‌ش نجومی می‌شه. مثلاً برای ۵۰۰ ترابایت در ماه، فرقش چند صد هزار دلاره.
بدون Key Deletion: GDPR ناقص می‌مونه چون داده‌ها قابل بازیابی می‌مونن.

پیامدها
چیزایی که به دست آوردیم:
هزینه Storage به شدت کم شد (Glacier تقریباً ۱۰ برابر ارزون‌تر از Standard هست)
کوئری‌های پیامای اخیر سریع موند
با GDPR سازگار شدیم
کاربر می‌تونه بکاپش رو برگردونه
چیزایی که از دست دادیم:
Restore از Glacier کند هست (۳-۵ ساعت)
Key Deletion پیچیدگی داره و اگه اشتباه انجام بشه، کاربر برای همیشه داده‌هاش رو از دست می‌ده
نگهداری Jobهای Archive نیاز به Monitoring دقیق داره

ADR-004: پشتیبانی از چندزبانگی، و Asset Pipeline

وضعیت: پذیرفته شده
تاریخ: ۱۴۰۳

زمینه و مسئله
پلتفرم ما باید بتونه بازی‌هایی که کاربرا می‌سازن رو روی ویندوز، لینوکس و مک اجرا کنه.
از اون طرف، کاربرا از کشورهای مختلفن و انتظار دارن رابط کاربری به زبان خودشون باشه.
یه مسئله دیگه هم Assetها هستن: کاربرا مدل سه‌بعدی، صدا، انیمیشن و تکسچر با فرمت‌های مختلف (FBX، OBJ، PNG، WAV و ...) آپلود می‌کنن.
موتور بازی ما نمی‌تونه همه این فرمت‌ها رو مستقیم بخونه. باید یه لایه میانی داشته باشیم که اینا رو به فرمت استاندارد تبدیل کنه.
سه تا مشکل اصلی داریم:
اول، چندزبانگی. رابط کاربری ادیتور و بازی باید به زبان کاربر باشه. اگه کاربر فارسی‌زبانه، باید RTL باشه. اگه انگلیسی‌زبانه، LTR.
دوم، Cross-platform. بازی باید روی سه OS اجرا بشه. نمی‌شه برای هر کدوم جدا کد زد. باید یه بار بنویسیم و همه جا اجرا شه.
سوم، Asset Pipeline. فرمت‌های ورودی متنوعن. باید خودکار تبدیل بشن، بهینه بشن و تو CDN قرار بگیرن تا سریع لود بشن.

تصمیم
تصمیم ۱: i18next برای چندزبانگی + پشتیبانی RTL/LTR
توضیحات:
از کتابخانه i18next استفاده می‌کنیم. هر زبان یه فایل JSON جداگانه داره.
تشخیص زبان به صورت خودکار از مرورگر یا تنظیمات کاربر انجام می‌شه.
برای زبان‌های RTL (فارسی، عربی) کل رابط کاربری با CSS dir="rtl" برعکس می‌شه.
اعداد و تاریخ هم بر اساس زبان محلی نمایش داده می‌شن.
مزایا:
کاربر با زبان خودش کار می‌کنه، تجربه بهتری داره
افزودن زبان جدید فقط با اضافه کردن یه فایل JSON انجام می‌شه (بدون نسخه‌گذاری)
RTL/LTR خودکار بر اساس زبان انتخاب شده
معایب:
برای هر زبان یه فایل JSON جداگانه نیازه (نگهداری بیشتر)
ترجمه‌ها باید توسط انسان بازبینی بشن (کیفیت)
بعضی کامپوننت‌های شخص ثالث ممکنه با RTL سازگار نباشن


تصمیم 2: Asset Pipeline خودکار با Assimp + FFmpeg + S3 + CDN
توضیحات:
وقتی کاربر یه Asset آپلود می‌کنه (مثلاً یه مدل FBX)، یه صف تو Kafka ایجاد می‌شه.
یه Worker میاد و با Assimp (برای مدل‌های سه‌بعدی) یا FFmpeg (برای صدا و ویدیو) اون رو به فرمت استاندارد تبدیل می‌کنه: مدل‌ها به glTF،
صداها به OGG، تصاویر به WebP. بعد تو S3 ذخیره می‌شه و از طریق CDN توزیع می‌شه. تو دیتابیس فقط Metadata و لینک نگه‌داری می‌شه.
مزایا:
کاربر با هر فرمتی آپلود کنه، بازی اجرا می‌شه (فرمت‌ها خودکار تبدیل می‌شن)
فایل‌های بهینه‌شده سریع‌تر لود می‌شن (CDN + فرمت‌های سبک)
حجم ذخیره‌سازی کمتر می‌شه (فشرده‌سازی خودکار)
معایب:
زمان پردازش برای Assetهای سنگین (ممکنه چند دقیقه طول بکشه)
وابستگی به کتابخانه‌های خارجی مثل Assimp و FFmpeg
پیچیدگی مدیریت نسخه‌های مختلف Asset (کی، کِی، چی رو آپدیت کرد)


تصمیم ۴: ذخیره‌سازی Asset با نسخه‌بندی و CDN
توضیحات:
هر Asset یه نسخه داره. وقتی کاربر آپدیتش می‌کنه، نسخه جدید ذخیره می‌شه و نسخه قبلی هم باقی می‌مونه.
اینطوری پروژه‌هایی که از نسخه قدیمی استفاده می‌کنن خراب نمی‌شن. CDN هم با TTL مناسب کش می‌کنه تا سرعت لود بالا بره.
مزایا:
پروژه‌های قدیمی خراب نمی‌شن (هر پروژه به یه نسخه از Asset وابسته‌ست)
سرعت لود بالا (CDN از نزدیک‌ترین نقطه سرویس می‌ده)
کاربر می‌تونه به نسخه‌های قبلی Asset برگرده
معایب:
حجم ذخیره‌سازی بیشتر می‌شه (چون نسخه‌های قدیمی نگه داشته می‌شن)
مدیریت Cache Invalidation پیچیده‌تر می‌شه
هزینه CDN برای Assetهای حجیم بالاست


گزینه‌های بررسی‌شده
الف) Native برای هر OS (سه کدبیس جدا):
مزایا: بهترین Performance، دسترسی کامل به سخت‌افزار
معایب: سه برابر کار، نگهداری فاجعه، استخدام تیم برای هر OS

ب) استفاده از موتور آماده مثل Unity/Unreal:
مزایا: زیرساخت آماده، Cross-platform خودکار
معایب: وابستگی به شرکت خارجی، هزینه لایسنس، محدودیت در سفارشی‌سازی، ما نمی‌تونیم پلتفرم ساخت بازی باشیم (در واقع رقیب می‌شیم)

ج) تبدیل دستی Assetها توسط کاربر:
مزایا: سادگی پیاده‌سازی (کاربر خودش تبدیل می‌کنه)
معایب: کاربر غیرفنی نمی‌تونه، خطای زیاد، تجربه کاربری بد

د) بدون i18n (فقط انگلیسی):
مزایا: سادگی، هزینه کمتر
معایب: کاربرای غیرانگلیسی‌زبان نمی‌تونن استفاده کنن، بازار محدود می‌شه

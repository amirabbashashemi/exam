بخش اول: چک‌لیست ۵ ثانیه‌ای Testability (قبل از تحویل کد)
وقتی کد را نوشتید، این ۵ سوال را از خودتان بپرسید. اگر جواب هرکدام "نه" بود، نمره‌تان کم می‌شود:

آیا تمام وابستگی‌های کلاس از طریق Constructor تزریق می‌شوند؟
(اگر در جایی new کردید یا از ServiceLocator/Factory داخل متد استفاده کردید → غلط است. Constructor Injection اجباری است).

آیا به‌جای کلاس‌های Concrete، از اینترفیس استفاده کرده‌ام؟
(اگر کلاس شما به RealEmailSender و RealUserRepository وابسته است و نه به اینترفیس‌هایشان → تست با Stub ممکن نیست).

آیا از System.currentTimeMillis() یا new Date() یا LocalDateTime.now() بدون Clock استفاده کرده‌ام؟
(اگر بله → تست شما غیرقطعی (Non-deterministic) می‌شود و هر بار نتیجه‌ی متفاوتی دارد).

آیا متدهای تست من بدون نیاز به دیتابیس، شبکه، فایل‌سیستم یا Thread.sleep اجرا می‌شوند؟
(اگر برای اجرای تست نیاز به محیط خارجی دارید → Testability پایین است).

آیا کلاس اصلی (مثل RegistrationService) از if-else/switch برای انتخاب وابستگی‌ها یا منطق تجاری استفاده می‌کند؟
(اگر بله → یعنی Single Responsibility را نقض کرده‌اید و تست کردن آن سخت می‌شود).

🥈 بخش دوم: کلمات کلیدی جادویی برای پاسخ‌های تشریحی (تئوری محض)
اگر سوال تشریحی در مورد Testability آمد، حتماً این ۴ عبارت کلیدی را در پاسخ خود قالب کنید:

Dependency Injection (تزریق وابستگی):
"برای افزایش تست‌پذیری، تمام وابستگی‌ها باید از طریق Constructor یا Setter به کلاس تزریق شوند تا در محیط تست بتوانیم آنها را با Stub یا Mock جایگزین کنیم."

Seam (نقطه‌ی اتصال):
"یک Seam نقطه‌ای در کد است که می‌توانیم رفتار را بدون تغییر در کد اصلی تغییر دهیم. در معماری خوب، Constructor محل مناسبی برای ایجاد Seam است."

Observability (قابلیت مشاهده‌پذیری):
"سیستم باید به‌گونه‌ای طراحی شود که خروجی‌ها و حالت داخلی آن به‌راحتی قابل مشاهده و بررسی باشند تا تست‌ها بتوانند صحت عملکرد را تأیید کنند."

Test Double (جایگزین‌های تست):
"برای ایزوله کردن کلاس مورد نظر از همتایان واقعی، از Test Doubleها (مانند Stub، Mock، Fake) استفاده می‌کنیم تا وابستگی‌های خارجی را شبیه‌سازی کنیم."

🥉 بخش سوم: تله‌های مرگبار (نمره‌ی زیر ۵۰)
این اشتباهات را هرگز در آزمون Testability مرتکب نشوید:

استفاده از new برای ساخت وابستگی‌ها در داخل متدها:

java
EmailSender sender = new RealEmailSender(); // ❌ مرگبار!
این کار باعث می‌شود که در تست نتوانید Stub را جایگزین کنید.

استفاده از ServiceLoader یا Factory به‌صورت استاتیک در داخل متد:

java
EmailSender sender = EmailSenderFactory.getInstance(); // ❌ هنوز وابستگی پنهان است!
حتی اگر Factory باشد، باز هم وابستگی پنهان محسوب می‌شود. باید Factory را هم تزریق کنید.

استفاده از System.currentTimeMillis() یا LocalDateTime.now() بدون Clock:

java
long now = System.currentTimeMillis(); // ❌ تست غیرقطعی می‌شود
در تست، نمی‌توانید زمان را کنترل کنید و خروجی هر بار متفاوت است.

نوشتن Stub با Thread.sleep یا عملیات سنگین:

java
class StubEmailSender implements EmailSender {
    public void sendWelcome(String email) {
        Thread.sleep(1000); // ❌ تست را کند می‌کند!
    }
}
Stub باید سریع و سبک باشد.

استفاده از کلاس‌های Concrete به‌جای اینترفیس در نوع پارامترها:

java
public RegistrationService(RealEmailSender sender, RealUserRepository repo) // ❌
باید از اینترفیس استفاده کنید: EmailSender و UserRepository.

📜 خلاصه‌ی یک پاراگرافی برای شب امتحان (قابل حفظ کردن)
Testability یعنی "قابلیت نوشتن تست‌های سریع، ایزوله و قابل‌پیش‌بینی". برای رسیدن به آن، تمام وابستگی‌ها را از طریق Constructor تزریق کن و از اینترفیس به‌جای کلاس‌های Concrete استفاده کن. هیچ‌وقت از System.currentTimeMillis() یا new Date() استفاده نکن؛ به‌جای آن، Clock را تزریق کن تا در تست زمان را ثابت نگه داری. از Stubهای سریع و بدون I/O برای شبیه‌سازی وابستگی‌های خارجی استفاده کن. اگر برای اجرای تست نیاز به دیتابیس، شبکه یا فایل‌سیستم داری، یعنی Testability ات پایین است و باید وابستگی‌ها را با Stub جایگزین کنی.

🔥 نکته‌ی طلایی ویژه برای مقایسه (اگر در آزمون پرسیدند)
ویژگی	Maintainability	Modifiability	Testability
تمرکز اصلی	سهولت درک و اصلاح کد منبع	هزینه‌ی تغییرات در سیستم زنده	سهولت نوشتن تست‌های خودکار
ابزار اصلی	SOLID, Design Patterns	پیکربندی پویا (Map, Config)	تزریق وابستگی، اینترفیس، Clock
زمان اعمال	زمان توسعه (Development)	زمان اجرا (Runtime)	زمان تست (Testing)
سوال کلیدی	"برای افزودن قابلیت، چند کلاس تغییر می‌کند؟"	"برای تغییر نرخ، نیاز به Deploy دارم؟"	"آیا می‌توانم این کلاس را بدون دیتابیس تست کنم؟"
نکته‌ی طلایی	از Strategy و Template Method استفاده کن	از Map و refreshRates استفاده کن	از Constructor Injection و Clock استفاده کن
💡 نکته‌ی نهایی (برای امتیاز اضافی در آزمون)
اگر Examiner از شما پرسید: "چه تفاوتی بین Stub و Mock وجود دارد؟" پاسخ دهید:

Stub یک پیاده‌سازی ساده و از پیش تعیین‌شده از یک اینترفیس است که رفتاری ثابت (مثلاً همیشه یک مقدار خاص) برمی‌گرداند و معمولاً وضعیت (State) ندارد. اما Mock شیءای است که انتظارات ما را در مورد نحوه‌ی فراخوانی متدها بررسی می‌کند (مثلاً چند بار متد صدا زده شده، با چه پارامترهایی). در آزمون با محدودیت Standard Library، ما فقط از Stub استفاده می‌کنیم (چون کتابخانه‌ی Mock مثل Mockito مجاز نیست). اما با گفتن این تفاوت، نشان می‌دهید که دانش عمیقی دارید.

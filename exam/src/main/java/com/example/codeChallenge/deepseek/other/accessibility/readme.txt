نکات طلایی معماری Accessibility (Java 21 Standard Library)
بر اساس آنچه در این سشن و کتاب Java 21 NFR Handbook پوشش دادیم، این ۷ نکته‌ی طلایی را به‌عنوان خلاصه‌ی نهایی برای مبحث Accessibility در سطح معماری به شما تقدیم می‌کنم. این نکات دقیقاً همان چیزهایی است که یک Examiner در سطح ۱۰ به دنبال آن است.

۱. سطوح لاگ را با Enum و index (یا ordinal) مدیریت کن، اما از volatile غافل نشو
از Enum برای تعریف سطوح (DEBUG, INFO, ERROR) استفاده کن و با int index ترتیب اولویت را مشخص کن.

برای تغییر سطح در حین اجرا (Dynamic Level Change)، متغیر logLevel را volatile تعریف کن تا در محیط‌های هم‌روند، تغییرات فوراً در همه‌ی تردها قابل‌مشاهده باشد.

نکته‌ی طلایی: شرط فیلتر را در ابتدای متدهای debug، info و error بگذار. ERROR همیشه باید لاگ شود (چون بحرانی است).

۲. برای هم‌روندی (Concurrency) حتماً synchronized یا FileLock بگذار
اگر چند ترد همزمان در حال نوشتن لاگ در یک فایل هستند، حتماً متد logToFile را synchronized کن تا فایل خراب (Corrupt) نشود.

نکته‌ی طلایی: Files.writeString با APPEND به‌تنهایی در محیط هم‌روند امن نیست؛ باید از synchronized برای ترتیب‌دهی نوشتن استفاده کنی.

۳. برای تشخیص تراکنش‌ها در گزارش، از یک الگوی ثابت (Prefix) استفاده کن (مثلاً "TRX:")
برای تولید گزارش آماری دقیق، هرگز به کلماتی مثل "successful" یا "failed" اکتفا نکن، چون ممکن است در پیام‌های خطا هم تکرار شوند.

تمام تراکنش‌ها را با یک پیشوند استاندارد مثل "TRX:" شروع کن. سپس در generateReport فقط خطوط حاوی این پیشوند را فیلتر کن.

نکته‌ی طلایی: با این کار، total دقیقاً برابر تعداد تراکنش‌ها می‌شود و خطوط سیستمی (DEBUG و INFOهای معمولی) در آمار لحاظ نمی‌شوند.

۴. پیام‌های ERROR را قابل‌اجرا (Actionable) کن
شرط اصلی Accessibility برای کاربر غیرفنی این است که بداند «الان باید چکار کند؟».

در پیام‌های ERROR، همیشه یک راهنمای عملی اضافه کن. مثلاً:
" | Action: Check transaction ID and retry, or contact support."

نکته‌ی طلایی: این کار، لاگ را از یک متن صرفاً اطلاعاتی به یک دستورالعمل عملیاتی تبدیل می‌کند که ارزش Accessibility را چندین برابر بالا می‌برد.

۵. در گزارش‌دهی (Report)، از total == 0 محافظت کن تا NaN نزنی
اگر هیچ تراکنشی پردازش نشده باشد، total برابر صفر است و success / total * 100 می‌شود NaN یا Infinity.

نکته‌ی طلایی: همیشه از یک شرط if (total == 0) percentage = 0.0 استفاده کن تا خروجی گزارش همیشه یک عدد معتبر باشد.

۶. آرگومان‌ها (args) را با کاما و فاصله (", ") از هم جدا کن
آرگومان‌های ورودی لاگ را نباید پشت سر هم بدون جداکننده چسباند.

استفاده از for با شرط if (i > 0) sb.append(", ") باعث می‌شود خروجی args خوانا و حرفه‌ای به نظر برسد.

نکته‌ی طلایی: خوانایی لاگ، یکی از ارکان اصلی Accessibility است؛ لاگ باید برای چشم انسان (و نه فقط ماشین) خواناترین حالت ممکن را داشته باشد.

۷. معماری Accessibility یعنی «مخاطب‌شناسی» در طراحی خروجی
DEBUG: فقط برای توسعه‌دهندگان (جزئیات فنی کامل).

INFO: برای اپراتورها (خلاصه‌ی وضعیت، تراکنش‌های موفق).

ERROR: برای همه (مدیران، اپراتورها، پشتیبانی) همراه با راهنمای عملی.

نکته‌ی طلایی: یک سیستم با Accessibility بالا، نیازی به همراه داشتن مستندات جداگانه برای درک لاگ‌های خود ندارد. خود لاگ‌ها باید «خودتوضیح» (Self-Descriptive) باشند.

خلاصه‌ی یک‌خطی برای روز آزمون (Cheat Sheet):
«سطوح را با Enum و Index جدا کن، با volatile تغییر پویا بده، با synchronized بنویس، با Prefix (TRX:) گزارش بگیر، به ERROR راهنمای عملی اضافه کن، از تقسیم بر صفر جلوگیری کن، و آرگومان‌ها را خوانا بنویس.»

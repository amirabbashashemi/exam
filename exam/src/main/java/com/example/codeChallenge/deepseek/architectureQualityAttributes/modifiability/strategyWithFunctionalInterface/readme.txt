🥇 بخش اول: چک‌لیست ۵ ثانیه‌ای Modifiability (قبل از تحویل کد)
وقتی کد را نوشتید، این ۵ سوال را از خودتان بپرسید. اگر جواب هرکدام "نه" بود، نمره‌تان کم می‌شود:

آیا برای تغییر یک عدد یا نرخ (مثل تخفیف ۲۰٪ به ۲۵٪) مجبورم کد را کامپایل و Deploy کنم؟
(اگر بله → Modifiability شما صفر است. باید از Map یا فایل کانفیگ استفاده کنید).

آیا متد refresh یا updateConfig عمومی دارم که Admin یا اپلیکیشن دیگر بتواند بدون رستارت سرور، آن را صدا بزند؟
(اگر نه → یعنی تغییرات فقط در زمان Deploy ممکن است و نمره‌ی کامل نمی‌گیرید).

اگر یک کلید جدید (مثل نوع کاربر Student) به پیکربندی اضافه شود، آیا سیستم بدون تغییر در کد منبع و بدون خطا کار می‌کند؟
(اگر نه → یعنی معماری شما برای افزودن نوع جدید وابسته به تغییر کلاس است).

آیا از Map.getOrDefault یا Optional برای مدیریت کلیدهای نال استفاده کرده‌ام؟
(اگر نه و از get() خام استفاده کنید، با NullPointerException کرش می‌کند).

آیا لایه‌ی سرویس (مثل DiscountService) از if-else یا switch برای تشخیص نوع کاربر استفاده می‌کند؟
(اگر بله → غلط است. باید همه‌چیز را به Map بسپارید).

🥈 بخش دوم: کلمات کلیدی جادویی برای پاسخ‌های تشریحی (تئوری محض)
اگر سوال تشریحی در مورد Modifiability آمد، حتماً این ۴ عبارت کلیدی را در پاسخ خود قالب کنید:

Runtime Configuration (پیکربندی در زمان اجرا):
"تغییرات باید از طریق به‌روزرسانی یک منبع خارجی (دیتابیس، فایل، یا API مدیریتی) اعمال شوند، نه از طریق تغییر کد منبع."

Cost of Change (هزینه‌ی تغییر):
"Modifiability به معنای به حداقل رساندن هزینه‌ی پیاده‌سازی، تست و استقرار یک تغییر است. ایده‌آل‌ترین حالت، تغییر با هزینه‌ی صفر (بدون Deploy) است."

Deployment Independence (استقلال از استقرار):
"سیستم باید به‌گونه‌ای طراحی شود که تغییرات پیکربندی، نیازی به ری‌استارت یا کامپایل مجدد نداشته باشند."

Decoupling (جداسازی):
"منطق انتخاب (نوع کاربر) از منطق اجرا (محاسبه‌ی تخفیف) جدا شده است تا بتوان هرکدام را بدون تأثیر بر دیگری تغییر داد."

🥉 بخش سوم: تله‌های مرگبار (نمره‌ی زیر ۵۰)
این اشتباهات را هرگز در آزمون Modifiability مرتکب نشوید:

ذخیره‌ی مقادیر پیکربندی در static final: اگر نرخ تخفیف را public static final double VIP_RATE = 0.8; بنویسید، برای تغییر آن مجبور به کامپایل مجدد هستید. (این دقیقاً نقطه‌ی مقابل Modifiability است).

استفاده از System.getProperty() در ابتدای برنامه و نخواندن دوباره آن: اگر فقط یک بار در static بلوک بخوانید، برای تغییر نیاز به ری‌استارت دارید.

پرتاب Exception به جای Fallback: اگر یک کلید در Map نبود و شما throw new IllegalArgumentException کردید، سیستم کرش می‌کند. همیشه از getOrDefault یا استراتژی پیش‌فرض استفاده کنید.

استفاده از HashMap ساده به جای ConcurrentHashMap: اگر سیستم شما چندنخی (Multi-threaded) باشد، HashMap ممکن است باعث خرابی داده‌ها شود. (حتی اگر صورت سوال نگفته باشد، استفاده از ConcurrentHashMap یک نکته‌ی امتیازی مثبت است).

📜 خلاصه‌ی یک پاراگرافی برای شب امتحان (قابل حفظ کردن)
Modifiability یعنی "تغییر با کمترین هزینه". برای رسیدن به آن، هیچ‌وقت مقادیر متغیر (مثل نرخ تخفیف، آدرس‌ها، یا کلیدهای ویژگی‌ها) را به‌صورت هاردکد در کد منبع ننویس. همیشه آنها را در یک Map یا Properties پویا قرار بده و یک متد عمومی مانند refreshConfig یا updateRates برای به‌روزرسانی آن در نظر بگیر. در صورت عدم وجود کلید درخواستی، هیچ‌گاه کرش نکن؛ از یک مقدار پیش‌فرض (Default) استفاده کن و با getOrDefault خطا را مدیریت کن. لایه‌ی سرویس (Orchestrator) باید کاملاً از if-else و switch خالی باشد و تمام تصمیم‌گیری‌ها را بر اساس جستجو در Map انجام دهد.

🔥 نکته‌ی طلایی ویژه برای مقایسه (اگر در آزمون پرسیدند)
ویژگی	Maintainability	Modifiability
تمرکز	درک و رفع باگ / افزودن قابلیت در کد منبع	هزینه و ریسک اعمال تغییرات در سیستم زنده
زمان تغییر	زمان کامپایل (Compile-time)	زمان اجرا (Runtime)
ابزار اصلی	SOLID, Design Patterns (Strategy, Template)	پیکربندی پویا (Dynamic Config), Registry, Map
مثال	افزودن یک کلاس جدید برای درگاه پرداخت	تغییر نرخ تخفیف بدون ری‌استارت سرور
سوال کلیدی	"برای افزودن این قابلیت، چند کلاس باید تغییر کنند؟"	"برای تغییر این نرخ، آیا نیاز به Deploy دارم؟"

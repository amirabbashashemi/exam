🥇 بخش اول: چک‌لیست ۵ ثانیه‌ای Deployability (قبل از تحویل کد)
وقتی کد را نوشتید، این ۵ سوال را از خودتان بپرسید. اگر جواب هرکدام "نه" بود، نمره‌تان کم می‌شود:

آیا تمام تنظیمات وابسته به محیط (مثل آدرس دیتابیس، پورت، کلیدهای API) از کد جدا شده‌اند؟
(اگر در کد String url = "jdbc:mysql://localhost:3306/db" نوشته‌اید → غلط است).

آیا با تغییر یک متغیر محیطی (مثل ENV=prod یا config_url=/path/to/config.properties) می‌توانم بدون تغییر کد، محیط را عوض کنم؟
(اگر برای تغییر محیط نیاز به کامپایل مجدد دارید → Deployability پایین است).

آیا اگر متغیر محیطی تنظیم نشود، برنامه با یک مقدار پیش‌فرض (مثل dev) کار می‌کند و کرش نمی‌کند؟
(اگر برنامه بدون تنظیم متغیر اجرا نشود → تجربه‌ی توسعه‌دهنده ضعیف است).

آیا برای اضافه کردن یک محیط جدید (مثل Staging)، فقط کافی است یک فایل کانفیگ جدید اضافه کنم و نیازی به تغییر کد منبع ندارم؟
(اگر برای اضافه کردن محیط جدید نیاز به تغییر کد دارید → مقیاس‌پذیری عملیاتی پایین است).

آیا از java.util.Properties یا ResourceBundle برای خواندن فایل‌های کانفیگ استفاده کرده‌ام و از split("=") دستی پرهیز کرده‌ام؟
(اگر فایل را خط‌به‌خط با split می‌خوانید → ممکن است با فایل‌های پیچیده‌تر دچار مشکل شوید).

🥈 بخش دوم: کلمات کلیدی جادویی برای پاسخ‌های تشریحی (تئوری محض)
اگر سوال تشریحی در مورد Deployability آمد، حتماً این ۴ عبارت کلیدی را در پاسخ خود قالب کنید:

Externalized Configuration (پیکربندی خارجی):
"تنظیمات وابسته به محیط نباید در کد منبع باشند. آنها باید از طریق متغیرهای محیطی، فایل‌های Properties، یا آرگومان‌های JVM تأمین شوند تا بتوان بدون تغییر کد، در محیط‌های مختلف استقرار یافت."

Environment Abstraction (انتزاع محیط):
"سیستم باید از یک متغیر محیطی مثل ENV یا PROFILE برای تشخیص محیط (dev/test/prod) استفاده کند و بر اساس آن، پیکربندی مناسب را بارگذاری کند."

Zero-Downtime Deployment (استقرار بدون توقف):
"معماری باید به‌گونه‌ای باشد که استقرار نسخه‌ی جدید، نیازی به توقف سرویس نداشته باشد و کاربران نهایی قطعی را تجربه نکنند (با استفاده از Blue-Green یا Rolling Deployment)."

Rollback Capability (قابلیت برگشت):
"سیستم باید امکان برگشت به نسخه‌ی قبلی را به‌سادگی فراهم کند؛ مثلاً با نگهداری نسخه‌های قبلی JAR یا پشتیبانی از استراتژی‌های Deployment که امکان برگشت سریع را دارند."

🥉 بخش سوم: تله‌های مرگبار (نمره‌ی زیر ۵۰)
این اشتباهات را هرگز در آزمون Deployability مرتکب نشوید:

هاردکد کردن مقادیر محیطی در کد:

java
String dbUrl = "jdbc:mysql://prod-db:3306/mydb"; // ❌ فقط برای Production کار می‌کند
استفاده از if-else برای تشخیص محیط در کد:

java
if (env.equals("prod")) { ... } else if (env.equals("test")) { ... } // ❌
این کار باعث می‌شود که برای هر محیط جدید، کد تغییر کند.

عدم ارائه‌ی مقدار پیش‌فرض:
اگر متغیر محیطی تنظیم نشود، برنامه با NullPointerException کرش کند. همیشه یک مقدار پیش‌فرض (مثل dev) داشته باشید.

استفاده از File و مسیرهای مطلق به‌جای getResourceAsStream:

java
FileInputStream fis = new FileInputStream("/etc/app/config.properties"); // ❌ در سیستم‌عامل‌های دیگر کار نمی‌کند
از getResourceAsStream استفاده کنید تا فایل در Classpath پیدا شود.

ذخیره‌ی رمزهای عبور (Passwords) در فایل‌های کانفیگ به‌صورت متن‌باز (Plain Text):
اگرچه در آزمون به آن اشاره نمی‌شود، اما در دنیای واقعی، باید از ابزارهای مدیریت اسرار (Secrets Management) مثل HashiCorp Vault استفاده کنید.

📜 خلاصه‌ی یک پاراگرافی برای شب امتحان (قابل حفظ کردن)
Deployability یعنی "قابلیت استقرار آسان، سریع و ایمن در هر محیطی". برای رسیدن به آن، تمام تنظیمات وابسته به محیط را از کد جدا کن و از متغیرهای محیطی، فایل‌های properties، یا آرگومان‌های JVM برای تأمین آنها استفاده کن. از یک متغیر محیطی مثل ENV برای تشخیص محیط استفاده کن و بر اساس آن، فایل کانفیگ مناسب را بارگذاری کن (مثلاً smtp-dev.properties یا smtp-prod.properties). همیشه یک مقدار پیش‌فرض (مثل dev) داشته باش تا بدون نیاز به تنظیم متغیر، برنامه در محیط توسعه اجرا شود. برای خواندن فایل‌های کانفیگ، از Properties و getResourceAsStream استفاده کن و از File و مسیرهای مطلق پرهیز کن. به‌یاد داشته باش که اضافه کردن یک محیط جدید باید فقط با اضافه کردن یک فایل جدید امکان‌پذیر باشد، نه با تغییر کد.

💡 نکته‌ی نهایی (برای امتیاز اضافی در آزمون)
اگر Examiner از شما پرسید: "چه تفاوتی بین System.getenv() و System.getProperty() در Deployability وجود دارد؟" پاسخ دهید:

System.getenv() متغیرهای محیطی سیستمعامل را می‌خواند (مثل ENV=prod) و برای تنظیمات ثابت و امنیتی (مثل رمزهای عبور) مناسب است. اما System.getProperty() مقادیری که با آرگومان‌های JVM (مثل -Dconfig.url=/path/to/config.properties) تنظیم شده‌اند را می‌خواند و برای تنظیمات موقتی یا تنظیماتی که نیاز به تغییر در حین اجرا دارند، مناسب‌تر است. در عمل، معمولاً هر دو را با اولویت‌بندی ترکیب می‌کنیم (اول System.getProperty، بعد System.getenv، و در نهایت مقدار پیش‌فرض).

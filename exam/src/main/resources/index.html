Deployability

نکات

جداسازی تمام تنظیمات وابسته به محیط (مثل آدرس دیتابیس، پورت، کلیدهای API)

یا با تغییر یک متغیر محیطی مثل ENV=prod یا config.properties می‌توانم بدون تغییر کد، محیط را عوض کنم؟

آیا اگر متغیر محیطی تنظیم نشود، برنامه با یک مقدار پیش‌فرض (مثل dev) کار می‌کند؟

آیا برای اضافه کردن یک محیط جدید (مثل Staging)، فقط کافی است یک فایل کانفیگ جدید اضافه کنم و نیازی به تغییر کد منبع ندارم؟

آیا از java.util.Properties یا ResourceBundle برای خواندن فایل‌های کانفیگ استفاده کرده‌ام و از split("=") دستی پرهیز کرده‌ام؟

کلمات کلیدی

Externalized Configuration (پیکربندی خارجی):

"تنظیمات وابسته به محیط نباید در کد منبع باشند. آنها باید از طریق متغیرهای محیطی، فایل‌های Properties، یا آرگومان‌های JVM تأمین شوند تا بتوان بدون تغییر کد، در محیط‌های مختلف استقرار یافت."

Environment Abstraction (انتزاع محیط):

"سیستم باید از یک متغیر محیطی مثل ENV یا PROFILE برای تشخیص محیط (dev/test/prod) استفاده کند و بر اساس آن، پیکربندی مناسب را بارگذاری کند."

Zero-Downtime Deployment (استقرار بدون توقف):

"معماری باید به‌گونه‌ای باشد که استقرار نسخه‌ی جدید، نیازی به توقف سرویس نداشته باشد و کاربران نهایی قطعی را تجربه نکنند (با استفاده از Blue-Green یا Rolling Deployment)."

Rollback Capability (قابلیت برگشت):

"سیستم باید امکان برگشت به نسخه‌ی قبلی را به‌سادگی فراهم کند؛ مثلاً با نگهداری نسخه‌های قبلی JAR یا پشتیبانی از استراتژی‌های Deployment که امکان برگشت سریع را دارند."

تله‌ها

هاردکد کردن مقادیر محیطی در کد:

String dbUrl = "jdbc:mysql://prod-db:3306/mydb"; // ❌ فقط برای Production کار می‌کند

استفاده از if-else برای تشخیص محیط در کد:

if (env.equals("prod")) { ... } else if (env.equals("test")) { ... } // ❌

این کار باعث می‌شود که برای هر محیط جدید، کد تغییر کند.

عدم ارائه‌ی مقدار پیش‌فرض:

اگر متغیر محیطی تنظیم نشود، برنامه با NullPointerException کرش کند. همیشه یک مقدار پیش‌فرض (مثل dev) داشته باشید.

استفاده از File و مسیرهای مطلق به‌جای getResourceAsStream:

FileInputStream fis = new FileInputStream("/etc/app/config.properties"); // ❌ در سیستم‌عامل‌های دیگر کار نمی‌کند

از getResourceAsStream استفاده کنید تا فایل در Classpath پیدا شود.

ذخیره‌ی رمزهای عبور (Passwords) در فایل‌های کانفیگ به‌صورت متن‌باز (Plain Text):

اگرچه در آزمون به آن اشاره نمی‌شود، اما در دنیای واقعی، باید از ابزارهای مدیریت اسرار (Secrets Management) مثل HashiCorp Vault استفاده کنید.

خلاصه

Deployability یعنی "قابلیت استقرار آسان، سریع و ایمن در هر محیطی".

برای رسیدن به آن، تمام تنظیمات وابسته به محیط را از کد جدا کن و از متغیرهای محیطی، فایل‌های properties، یا آرگومان‌های JVM برای تأمین آنها استفاده کن.

از یک متغیر محیطی مثل ENV برای تشخیص محیط استفاده کن و بر اساس آن، فایل کانفیگ مناسب را بارگذاری کن (مثلاً smtp-dev.properties یا smtp-prod.properties).

همیشه یک مقدار پیش‌فرض (مثل dev) داشته باش تا بدون نیاز به تنظیم متغیر، برنامه در محیط توسعه اجرا شود.

برای خواندن فایل‌های کانفیگ، از Properties و getResourceAsStream استفاده کن و از File و مسیرهای مطلق پرهیز کن.

به‌یاد داشته باش که اضافه کردن یک محیط جدید باید فقط با اضافه کردن یک فایل جدید امکان‌پذیر باشد، نه با تغییر کد.

Extendability | Interoperability

نکات

Abstraction (اینترفیس/کلاس انتزاعی) | Polymorphism (چندریختی) | Inversion (وارونگی وابستگی - Constructor Injection) | Discovery (کشف خودکار - ServiceLoader)

آیا برای اضافه کردن یک فرمت جدید (مثل JSON یا XML)، نیازی به تغییر در کلاس اصلی (مثلاً PaymentService) دارم؟ (اگر بله → یعنی وابستگی به فرمت‌ها در لایه‌ی سرویس باقی مانده است و Strategy Pattern را درست پیاده نکرده‌اید).

آیا از if-else یا switch برای تشخیص نوع فرمت استفاده کرده‌ام؟ (اگر بله → غلط است. باید از Map < Enum, Formatter> استفاده کنید).

اگر یک فرمت پشتیبانی نشود، آیا سیستم کرش می‌کند یا یک پیام خطای مناسب برمی‌گرداند؟ (اگر کرش کند → مدیریت خطا ضعیف است. باید یک Fallback داشته باشید).

آیا جداکننده‌ها و فرمت‌ها در کد هاردکد شده‌اند؟ (اگر بله → تغییر فرمت‌ها سخت است. می‌توانید آنها را به‌عنوان پارامتر یا از پیکربندی بخوانید).

آیا وابستگی‌ها (مثل PaymentFormatterService) از طریق Constructor تزریق می‌شوند؟ (اگر نه → تست‌پذیری پایین است).

تله‌ها

String result = id + "|" + amount + "|" + currency; // ❌ بهتر است جداکننده‌ها را به‌عنوان فیلد کلاس یا از پیکربندی بخوانید.

استفاده از if-else برای تشخیص فرمت: if (format.equals("LEGACY")) { ... } else if (format.equals("MODERN")) { ... } // ❌ به‌جای آن از Map < Enum, Formatter> و Strategy Pattern استفاده کنید.

برگرداندن null در صورت نبود فرمت: if (formatter == null) return null; // ❌ باعث NPE می‌شود نمونه‌سازی چندباره در هر درخواست:

PaymentFormatterService service = new PaymentFormatterService(); // ❌ هر بار بهتر است یک نمونه‌ی Singleton یا تزریق شده استفاده شود.

نادیده گرفتن خروجی فرمت‌شده: formatterService.format(LEGACY, tx); // ❌ خروجی دور ریخته می‌شود خروجی را بگیرید و به سیستم خارجی ارسال کنید.

Maintainability

نکات

آیا برای افزودن یک قابلیت جدید، مجبورم بیش از ۱ کلاس را ویرایش کنم؟ (اگر بله → یعنی Shotgun Surgery دارید و Maintainability پایین است).

آیا کلاس‌های من به جای if-else/switch از پلی‌مورفیسم استفاده می‌کنند؟ (اگر switch در لایه Orchestrator یا Service دیدید → غلط است).

آیا لایه‌ی بالایی (مثلاً PaymentService) از جزئیات پیاده‌سازی لایه‌ی پایین (نوع عملیات‌ها) بی‌خبر است؟ (اگر Service بداند که AUTHORIZE با CAPTURE چه فرقی دارد → غلط است. فقط باید بگوید execute یا process).

آیا هر کلاس فقط یک دلیل برای تغییر دارد؟ (Single Responsibility) (اگر کلاس PaymentService هم مسئول پیدا کردن درگاه است و هم مسئول اجرای منطق تبدیل مقادیر → غلط است).

آیا از Enumها برای ثابت‌های ساده استفاده کردم یا برای رفتار؟ (در Maintainability سطح بالا، Enumها می‌توانند حامل رفتار باشند، مثل همان PaymentAction که داشت Handler را در خودش نگه می‌داشت).

کلمات کلیدی

اگر سوال تشریحی در مورد Maintainability آمد، حتماً این ۴ عبارت کلیدی را در پاسخ خود قالب کنید. Examiner دقیقاً به دنبال این کلمات می‌گردد:

Locality of Change (محلی‌سازی تغییر): "تغییر در یک نیاز کسب‌وکاری، تنها باید منجر به تغییر در یک ماژول یا یک کلاس خاص شود و اثرات جانبی بر ماژول‌های دیگر نداشته باشد."

Separation of Concerns (جداسازی دغدغه‌ها): "منطق انتخاب الگوریتم (نوع درگاه) از منطق اجرای الگوریتم (خود عملیات‌ها) و منطق Orchestration (ترتیب فراخوانی‌ها) کاملاً جدا شده‌اند."

Coupling vs Cohesion (وابستگی در مقابل انسجام): "ماژول‌ها باید وابستگی‌های کم (Loose Coupling) و انسجام داخلی بالا (High Cohesion) داشته باشند. به‌طوری که بتوان یک کلاس را بدون نگرانی از شکستن بقیه‌ی سیستم، جداگانه تست یا تعویض کرد."

Open/Closed Principle: "کلاس‌ها برای گسترش (Extension) باز هستند، اما برای تغییر (Modification) بسته. یعنی برای اضافه کردن رفتار جدید، کلاس موجود را ویرایش نمی‌کنیم، بلکه کلاس جدید می‌سازیم."

تله‌ها

ستفاده از instanceof یا getClass() برای تشخیص نوع اشیاء به جای پلی‌مورفیسم. (این یعنی معماری شما به کلی اشتباه است).

برگرداندن null از متدها به جای پرتاب Optional یا Exception. (چون باعث می‌شود کلاینت‌ها مجبور به بررسی null شوند و کد را شلوغ کند).

نوشتن کلاس‌های Utility با متدهای static برای منطق تجاری. (این کار تست‌پذیری را صفر می‌کند و وابستگی پنهان ایجاد می‌کند).

استفاده از String برای شناسایی نوع (مثل "CreditCard") به جای Enum. (چون خطاهای تایپی را در کامپایل تشخیص نمی‌دهد و نگهداری را سخت می‌کند).

Modifiability

نکات

آیا برای تغییر یک عدد یا نرخ (مثل تخفیف ۲۰٪ به ۲۵٪) مجبورم کد را کامپایل و Deploy کنم؟ (اگر بله → Modifiability شما صفر است. باید از Map یا فایل کانفیگ استفاده کنید).

آیا متد refresh یا updateConfig عمومی دارم که Admin یا اپلیکیشن دیگر بتواند بدون رستارت سرور، آن را صدا بزند؟ (اگر نه → یعنی تغییرات فقط در زمان Deploy ممکن است و نمره‌ی کامل نمی‌گیرید).

اگر یک کلید جدید (مثل نوع کاربر Student) به پیکربندی اضافه شود، آیا سیستم بدون تغییر در کد منبع و بدون خطا کار می‌کند؟ (اگر نه → یعنی معماری شما برای افزودن نوع جدید وابسته به تغییر کلاس است).

آیا از Map.getOrDefault یا Optional برای مدیریت کلیدهای نال استفاده کرده‌ام؟ (اگر نه و از get() خام استفاده کنید، با NullPointerException کرش می‌کند).

آیا لایه‌ی سرویس (مثل DiscountService) از if-else یا switch برای تشخیص نوع کاربر استفاده می‌کند؟ (اگر بله → غلط است. باید همه‌چیز را به Map بسپارید).

کلمات کلیدی

Runtime Configuration (پیکربندی در زمان اجرا): "تغییرات باید از طریق به‌روزرسانی یک منبع خارجی (دیتابیس، فایل، یا API مدیریتی) اعمال شوند، نه از طریق تغییر کد منبع."

Cost of Change (هزینه‌ی تغییر): "Modifiability به معنای به حداقل رساندن هزینه‌ی پیاده‌سازی، تست و استقرار یک تغییر است. ایده‌آل‌ترین حالت، تغییر با هزینه‌ی صفر (بدون Deploy) است."

Deployment Independence (استقلال از استقرار): "سیستم باید به‌گونه‌ای طراحی شود که تغییرات پیکربندی، نیازی به ری‌استارت یا کامپایل مجدد نداشته باشند."

Decoupling (جداسازی): "منطق انتخاب (نوع کاربر) از منطق اجرا (محاسبه‌ی تخفیف) جدا شده است تا بتوان هرکدام را بدون تأثیر بر دیگری تغییر داد."

تله‌ها

ذخیره‌ی مقادیر پیکربندی در static final: اگر نرخ تخفیف را public static final double VIP_RATE = 0.8; بنویسید، برای تغییر آن مجبور به کامپایل مجدد هستید. (این دقیقاً نقطه‌ی مقابل Modifiability است).

استفاده از System.getProperty() در ابتدای برنامه و نخواندن دوباره آن: اگر فقط یک بار در static بلوک بخوانید، برای تغییر نیاز به ری‌استارت دارید.

پرتاب Exception به جای Fallback: اگر یک کلید در Map نبود و شما throw new IllegalArgumentException کردید، سیستم کرش می‌کند. همیشه از getOrDefault یا استراتژی پیش‌فرض استفاده کنید.

استفاده از HashMap ساده به جای ConcurrentHashMap: اگر سیستم شما چندنخی (Multi-threaded) باشد، HashMap ممکن است باعث خرابی داده‌ها شود. (حتی اگر صورت سوال نگفته باشد، استفاده از ConcurrentHashMap یک نکته‌ی امتیازی مثبت است).

📜 خلاصه‌ی یک پاراگرافی Modifiability یعنی "تغییر با کمترین هزینه". برای رسیدن به آن، هیچ‌وقت مقادیر متغیر (مثل نرخ تخفیف، آدرس‌ها، یا

کلیدهای ویژگی‌ها) را به‌صورت هاردکد در کد منبع ننویس. همیشه آنها را در یک Map یا Properties پویا قرار بده و یک

متد عمومی مانند refreshConfig یا updateRates برای به‌روزرسانی آن در نظر بگیر. در صورت عدم وجود کلید درخواستی،

هیچ‌گاه کرش نکن؛ از یک مقدار پیش‌فرض (Default) استفاده کن و با getOrDefault خطا را مدیریت کن. لایه‌ی سرویس

(Orchestrator) باید کاملاً از if-else و switch خالی باشد و تمام تصمیم‌گیری‌ها را بر اساس جستجو در Map انجام دهد.

Portability

نکات

آیا برای ساخت مسیرها از Path.of() یا Paths.get() و resolve() استفاده کرده‌ام و از + و / یا \ هاردکد پرهیز کرده‌ام؟ (اگر در جایی "C:\\folder\\file.txt" یا "/var/log/file.txt" نوشته‌اید → غلط است).

آیا برای ایجاد پوشه از Files.createDirectories() استفاده کرده‌ام، نه mkdir یا Runtime.exec()؟ (اگر از Runtime.exec("mkdir -p") استفاده کرده‌اید → در ویندوز کار نمی‌کند).

آیا هنگام خواندن/نوشتن فایل، StandardCharsets.UTF_8 را به‌صورت صریح مشخص کرده‌ام؟ (اگر از new FileReader(file) بدون مشخص کردن encoding استفاده کرده‌اید → به encoding پیش‌فرض سیستم وابسته است).

آیا از System.lineSeparator() به‌جای \n برای خط جدید استفاده کرده‌ام؟ (اگر \n هاردکد کرده‌اید → در ویندوز (\r\n) مشکل ایجاد می‌کند).

آیا برای تاریخ و زمان از java.time با Clock تزریقی استفاده کرده‌ام و از new Date() یا Calendar پرهیز کرده‌ام؟ (اگر از new Date() استفاده کرده‌اید → به Locale و Timezone سیستم وابسته است).

کلمات کلیدی

Abstraction over OS (انتزاع از سیستمعامل): "سیستم باید از APIهای انتزاعی جاوا (مثل java.nio.file) استفاده کند تا از جزئیات سیستمعامل‌های مختلف (ویندوز، لینوکس، مک) جدا شود."

Encoding Independence (استقلال از کدگذاری): "همیشه هنگام کار با فایل‌ها، کدگذاری را به‌صورت صریح با StandardCharsets.UTF_8 مشخص کنید تا به کدگذاری پیش‌فرض سیستم وابسته نباشید."

Path Abstraction (انتزاع مسیر): "به‌جای هاردکد کردن جداکننده‌های مسیر (/ یا \)، از Path.resolve() یا File.separator استفاده کنید تا کد در همه‌ی سیستمعامل‌ها کار کند."

Configuration Externalization (برون‌سپاری پیکربندی): "مسیرها و تنظیمات وابسته به محیط را از کد جدا کنید و از طریق متغیرهای محیطی، Properties یا تزریق وابستگی به کلاس ارائه دهید."

تله‌ها

استفاده از File به‌جای Path و Files API: File file = new File("/var/log/app.log"); // ❌ وابسته به سیستم‌عامل همیشه از Path و Files استفاده کنید.

استفاده از Runtime.exec برای دستورات سیستمی: Runtime.getRuntime().exec("mkdir -p /var/log"); // ❌ در ویندوز کار نمی‌کند به‌جای آن از Files.createDirectories() استفاده کنید.

هاردکد کردن جداکننده‌ی مسیر: String path = "/var/" + "log/" + "file.txt"; // ❌ در ویندوز شکست می‌خورد استفاده از new FileReader(file) یا new FileWriter(file) بدون مشخص کردن encoding:

BufferedReader reader = new BufferedReader(new FileReader("file.txt")); // ❌ از Files.newBufferedReader(path, StandardCharsets.UTF_8) استفاده کنید.

استفاده از new Date() یا Calendar: String date = new Date().toString(); // ❌ وابسته به Locale و Timezone از java.time و Clock تزریقی استفاده کنید.

استفاده از کلاس‌های خاص JVM (مثل sun.* یا com.sun.*): اگر از کلاس‌های غیراستاندارد استفاده کنید، کد شما روی JVMهای دیگر (مثل OpenJ9 یا GraalVM) اجرا نمی‌شود.

Testability

نکات

آیا تمام وابستگی‌های کلاس از طریق Constructor تزریق می‌شوند؟ (اگر در جایی new کردید یا از ServiceLocator/Factory داخل متد استفاده کردید → غلط است. Constructor Injection اجباری است).

آیا به‌جای کلاس‌های Concrete، از اینترفیس استفاده کرده‌ام؟ (اگر کلاس شما به RealEmailSender و RealUserRepository وابسته است و نه به اینترفیس‌هایشان → تست با Stub ممکن نیست).

آیا از System.currentTimeMillis() یا new Date() یا LocalDateTime.now() بدون Clock استفاده کرده‌ام؟ (اگر بله → تست شما غیرقطعی (Non-deterministic) می‌شود و هر بار نتیجه‌ی متفاوتی دارد).

آیا متدهای تست من بدون نیاز به دیتابیس، شبکه، فایل‌سیستم یا Thread.sleep اجرا می‌شوند؟ (اگر برای اجرای تست نیاز به محیط خارجی دارید → Testability پایین است).

آیا کلاس اصلی (مثل RegistrationService) از if-else/switch برای انتخاب وابستگی‌ها یا منطق تجاری استفاده می‌کند؟ (اگر بله → یعنی Single Responsibility را نقض کرده‌اید و تست کردن آن سخت می‌شود).

کلمات کلیدی

Dependency Injection (تزریق وابستگی): "برای افزایش تست‌پذیری، تمام وابستگی‌ها باید از طریق Constructor یا Setter به کلاس تزریق شوند تا در محیط تست بتوانیم آنها را با Stub یا Mock جایگزین کنیم."

Seam (نقطه‌ی اتصال): "یک Seam نقطه‌ای در کد است که می‌توانیم رفتار را بدون تغییر در کد اصلی تغییر دهیم. در معماری خوب، Constructor محل مناسبی برای ایجاد Seam است."

Observability (قابلیت مشاهده‌پذیری): "سیستم باید به‌گونه‌ای طراحی شود که خروجی‌ها و حالت داخلی آن به‌راحتی قابل مشاهده و بررسی باشند تا تست‌ها بتوانند صحت عملکرد را تأیید کنند."

Test Double (جایگزین‌های تست): "برای ایزوله کردن کلاس مورد نظر از همتایان واقعی، از Test Doubleها (مانند Stub، Mock، Fake) استفاده می‌کنیم تا وابستگی‌های خارجی را شبیه‌سازی کنیم."

تله‌ها

استفاده از new برای ساخت وابستگی‌ها در داخل متدها: EmailSender sender = new RealEmailSender(); // ❌ مرگبار! این کار باعث می‌شود که در تست نتوانید Stub را جایگزین کنید.

استفاده از ServiceLoader یا Factory به‌صورت استاتیک در داخل متد: EmailSender sender = EmailSenderFactory.getInstance(); // ❌ هنوز وابستگی پنهان است! حتی اگر Factory باشد، باز هم وابستگی پنهان محسوب می‌شود. باید Factory را هم تزریق کنید.

استفاده از System.currentTimeMillis() یا LocalDateTime.now() بدون Clock: long now = System.currentTimeMillis(); // ❌ تست غیرقطعی می‌شود در تست، نمی‌توانید زمان را کنترل کنید و خروجی هر بار متفاوت است.

نوشتن Stub با Thread.sleep یا عملیات سنگین: class StubEmailSender implements EmailSender { public void sendWelcome(String email) { Thread.sleep(1000); // ❌ تست را کند می‌کند! } } Stub باید سریع و سبک باشد.

استفاده از کلاس‌های Concrete به‌جای اینترفیس در نوع پارامترها: public RegistrationService(RealEmailSender sender, RealUserRepository repo) // ❌ باید از اینترفیس استفاده کنید: EmailSender و UserRepository.

Availability

نکات

آیا برای ارتباط با سرویس‌های خارجی (API، دیتابیس، پیام‌رسان) از Retry با Backoff استفاده کرده‌ام؟ (اگر خطای موقت باعث از کار افتادن کل سیستم شود → غلط است. Retry با تأخیر تصاعدی الزامی است).

آیا برای جلوگیری از بار اضافی، از Circuit Breaker یا Rate Limiter استفاده کرده‌ام؟ (اگر یک سرویس کند، تمام رشته‌ها را قفل کند → غلط است. باید درخواست‌ها را محدود یا قطع کنید).

آیا Timeouts برای تمام فراخوانی‌های خارجی (HTTP، DB، File I/O) تنظیم شده‌اند؟ (اگر بدون Timeout منتظر بمانید → کل سیستم ممکن است هنگ کند).

آیا Health Check و Readiness/Liveness Probe برای سرویس تعریف شده‌اند؟ (اگر سرویس زنده است اما ترافیک را نمی‌تواند پاسخ دهد → باید از Liveness/Readiness استفاده کنید).

آیا Fallback (راه‌حل جایگزین) برای سناریوهای شکست در نظر گرفته شده است؟ (اگر سرویس اصلی در دسترس نباشد، آیا پاسخ پیش‌فرض یا کش شده ارائه می‌شود؟).

کلمات کلیدی

Resilience (تاب‌آوری): "سیستم باید بتواند در برابر شکست‌های موقت (مانند قطع شبکه یا کندی سرویس) مقاومت کند و بدون دخالت اپراتور به حالت عادی بازگردد."

Retry with Exponential Backoff: "برای افزایش دسترسی، درخواست‌های شکست‌خورده را با تأخیر تصاعدی مجدداً ارسال می‌کنیم تا از ازدحام بیشتر جلوگیری شود و شانس موفقیت افزایش یابد."

Circuit Breaker (مدارشکن): "اگر تعداد خطاها از آستانه‌ای عبور کند، مدار را باز می‌کنیم تا درخواست‌های جدید مستقیماً با خطا مواجه شوند و از فشار بیشتر به سرویس آسیب‌پذیر جلوگیری کنیم."

Graceful Degradation (کاهش کیفیت هوشمندانه): "به‌جای شکست کامل، سیستم باید با ارائه‌ی پاسخ‌های کش‌شده یا داده‌های خلاصه‌شده، حداقل عملکرد را حفظ کند تا تجربه‌ی کاربر کاملاً از بین نرود."

تله‌ها

نداشتن Timeout برای فراخوانی‌های خارجی:

String response = httpClient.get("https://api.example.com"); // ❌ بدون Timeout اگر پاسخ نیاید، ترد برای همیشه مسدود می‌شود و سیستم از کار می‌افتد.

Retry بی‌رویه و بدون Backoff: for (int i=0; i<5; i++) { callService(); // ❌ بی‌درنگ تکرار می‌کند } این کار سرویس مقصد را با ازدحام بیشتر مواجه می‌کند و وضعیت را بدتر می‌کند.

استفاده از Thread.sleep در Retry به‌جای ScheduledExecutor: Thread.sleep(2000); // ❌ ترد را قفل می‌کند و منابع را هدر می‌دهد باید از ابزارهای غیرمسدودکننده مانند Scheduler استفاده کنید.

عدم تفکیک Liveness و Readiness Probe: اگر فقط Liveness داشته باشید، سرویس ممکن است زنده باشد اما برای دریافت ترافیک آماده نباشد (مثلاً در حال گرم شدن). نادیده گرفتن Fallback برای سناریوهای حیاتی: مثلاً در سرویس پرداخت، اگر درگاه اصلی قطع است، باید به درگاه پشتیبان یا پاسخ کش‌شده تغییر مسیر دهید.

📜 خلاصه‌ی یک پاراگرافی (قابل حفظ کردن) Availability یعنی "سیستم همواره در دسترس باشد و در برابر شکست‌ها تاب‌آوری داشته باشد". برای رسیدن به آن، همیشه برای ارتباطات خارجی Timeout و Retry با Backoff تنظیم کنید تا از قفل شدن رشته‌ها جلوگیری شود. از Circuit Breaker برای قطع درخواست‌های بی‌نتیجه و Rate Limiter برای کنترل ترافیک استفاده کنید. Health Check (Liveness/Readiness) را تعریف کنید تا مدیریت خودکار سرویس ممکن شود. و همیشه یک Fallback (راه‌حل جایگزین) برای شرایط شکست در نظر بگیرید تا سیستم به‌جای شکست کامل، با کیفیت کاهش‌یافته به کار خود ادامه دهد.

Continuity

نکات

نکات

آیا سیستم به‌گونه‌ای طراحی شده که در صورت از کار افتادن یک منطقه (Region) یا دیتاسنتر، به‌طور خودکار به منطقه‌ی دیگر Failover کند؟ (اگر Failover دستی باشد یا اصلاً پشتیبانی نشود → غلط است. باید Active-Passive یا Active-Active داشته باشید).

آیا RTO (Recovery Time Objective) و RPO (Recovery Point Objective) به‌صورت کمی و مشخص تعریف شده‌اند (مثلاً RTO < 5 دقیقه، RPO < 1 ساعت) و سیستم قادر به تأمین آنهاست؟ (اگر این اعداد تعریف نشده باشند یا سیستم نتواند به آنها برسد → Continuity معنی ندارد).

آیا Replication داده‌ها (همزمان یا ناهمزمان) بین منطقه‌های اصلی و پشتیبان به‌درستی پیکربندی شده است؟ (اگر داده‌ها به منطقه‌ی دوم نسخه‌برداری نشوند → در زمان Failover، داده‌های زیادی از دست می‌رود).

آیا فرایند Failback (بازگشت به منطقه‌ی اصلی پس از رفع مشکل) نیز به‌صورت خودکار یا نیمه‌خودکار تعریف شده است؟ (اگر فقط Failover را طراحی کنید اما Failback را فراموش کنید → ممکن است سیستم در منطقه‌ی پشتیبان باقی بماند و عملکرد کاهش یابد).

آیا سناریوهای Disaster Recovery به‌صورت دوره‌ای (مثلاً هر ۶ ماه) تست می‌شوند تا اطمینان حاصل شود که در شرایط واقعی کار می‌کنند؟ (اگر هرگز تست نکنید → ممکن است در زمان واقعی متوجه شوید که Replication خراب است یا تنظیمات شبکه اشتباه است).

کلمات کلیدی

RTO (Recovery Time Objective): "حداکثر زمان مجاز برای بازیابی سیستم پس از یک فاجعه است. مثلاً اگر RTO = 5 دقیقه باشد، یعنی سیستم باید حداکثر ۵ دقیقه پس از قطعی، دوباره در دسترس قرار گیرد."

RPO (Recovery Point Objective): "حداکثر مقدار داده‌ای که می‌توانیم در زمان فاجعه از دست بدهیم. مثلاً RPO = 1 ساعت به این معناست که سیستم باید حداقل داده‌های یک ساعت آخر را حفظ کرده باشد و فقط داده‌های کمتر از ۱ ساعت ممکن است از دست بروند."

Active-Active vs. Active-Passive: "در حالت Active-Active، هر دو منطقه به‌طور همزمان ترافیک را پردازش می‌کنند و Failover تقریباً آنی است. در حالت Active-Passive، منطقه‌ی دوم فقط در زمان بروز مشکل فعال می‌شود و ممکن است چند دقیقه طول بکشد."

Disaster Recovery Plan (طرح بازیابی فاجعه): "مجموعه‌ای از رویه‌ها، ابزارها و پیکربندی‌ها است که تضمین می‌کند پس از یک حادثه‌ی بزرگ (مثل قطع برق، آتش‌سوزی، یا حمله‌ی سایبری)، سیستم بتواند در بازه‌ی زمانی تعیین‌شده (RTO) با کمترین از دست دادن داده (RPO) به حالت عادی بازگردد."

تله‌ها

Replication همزمان (Synchronous) بدون در نظر گرفتن تأخیر شبکه: هر تراکنش باید در هر دو منطقه تأیید شود // ❌ اگر فاصله‌ی جغرافیایی زیاد باشد، تأخیر شبکه (Latency) به شدت افزایش می‌یابد و عملکرد اصلی را مختل می‌کند. باید از Replication ناهمزمان با RPO مناسب استفاده کنید.

ذخیره‌سازی داده‌های پیکربندی (Config) در یک منطقه: اگر تنظیمات سرویس‌ها فقط در منطقه‌ی اصلی ذخیره شود و به منطقه‌ی دوم نسخه‌برداری نشود → در زمان Failover، سیستم با تنظیمات قدیمی یا بدون تنظیمات راه‌اندازی می‌شود.

آزمایش نکردن Failover در محیط تولید (یا محیط مشابه): اگر Failover را فقط روی کاغذ طراحی کنید و هرگز اجرا نکنید → احتمال شکست در روز حادثه بسیار بالاست.

نادیده گرفتن وابستگی‌های خارجی (مثل DNS، CDN، یا APIهای شخص ثالث): اگر منطقه‌ی اصلی قطع شود، آیا DNS به‌طور خودکار به IP منطقه‌ی دوم اشاره می‌کند؟ آیا APIهای خارجی نیز در منطقه‌ی دوم در دسترس هستند؟

نداشتن Playbook مستند برای سناریوهای مختلف: اگر مستندات واضحی برای Failover، Failback، و تست‌های دوره‌ای نداشته باشید → در زمان بحران، تیم سردرگم می‌شود و زمان بازیابی افزایش می‌یابد.

خلاصه

📜 خلاصه‌ی یک پاراگرافی برای شب امتحان (قابل حفظ کردن) Continuity یعنی "قابلیت ادامه‌ی فعالیت سیستم با حداقل اختلال، حتی پس از وقوع فاجعه‌هایی مثل قطعی منطقه، خرابی دیتاسنتر، یا حملات سایبری". برای رسیدن به آن، ابتدا RTO (زمان بازیابی) و RPO (از دست دادن داده) را به‌صورت کمی تعیین کنید (مثلاً RTO < 5 دقیقه و RPO < 1 ساعت). سپس سیستم را به‌صورت Active-Passive یا Active-Active در دو منطقه‌ی جغرافیایی مستقل طراحی کنید و Replication داده‌ها را با توجه به RPO پیکربندی کنید (معمولاً ناهمزمان). Failover باید کاملاً خودکار باشد و با استفاده از ابزارهایی مثل Load Balancer، Health Checks، و DNS مدیریت شود. همچنین Failback را نیز برای بازگشت به منطقه‌ی اصلی پس از رفع مشکل طراحی کنید. مهم‌تر از همه، به‌طور دوره‌ای (مثلاً هر ۶ ماه) تمرین Disaster Recovery انجام دهید تا از صحت پیکربندی‌ها و فرایندها اطمینان حاصل کنید و مستندات به‌روز باشند.

Elasticity

نکات

آیا سیستم بر اساس معیارهای مشخص (مثل CPU Usage > 70% یا Queue Length > 1000) به‌طور خودکار تعداد نمونه‌ها را افزایش می‌دهد؟ (اگر Scaling دستی است یا معیار مشخصی ندارد → غلط است. Auto-Scaling بر اساس متریک‌های واقعی الزامی است).

آیا عملیات Scale Up در کمتر از ۲ دقیقه انجام می‌شود و سیستم در این بازه، بار اضافی را تحمل می‌کند؟ (اگر زمان راه‌اندازی نمونه‌های جدید بیش از ۲ دقیقه باشد → کاربران در این فاصله با کندی یا خطا مواجه می‌شوند).

آیا فرایند Scale Down به‌صورت Graceful انجام می‌شود و درخواست‌های در حال پردازش قطع نمی‌شوند؟ (اگر نمونه‌ها بلافاصله کشته شوند → کاربر خطا می‌بیند. باید از Connection Draining یا Shutdown Hooks استفاده کنید).

آیا معیارهای Scaling (آستانه‌ها، دوره‌ی ارزیابی، تعداد حداقل و حداکثر نمونه‌ها) قابل پیکربندی (Configurable) هستند و در کد Hard-Coded نشده‌اند؟ (اگر برای تغییر آستانه‌ها نیاز به Deploy جدید دارید → Elasticity انعطاف‌پذیر نیست).

آیا از Cooldown Period (دوره‌ی خنک‌سازی) برای جلوگیری از نوسانات بی‌رویه (Thrashing) استفاده شده است؟ (اگر بعد از هر Scale Up بلافاصله دوباره تصمیم‌گیری شود → سیستم مدام بالا و پایین می‌شود و بی‌ثبات می‌گردد).

کلمات کلیدی

Resilience4J (یا Hystrix) برای مدیریت بار و مقاومت: "برای جلوگیری از اثر دومینو و مدیریت بار اضافی، از Resilience4J استفاده می‌کنیم که امکاناتی مثل Circuit Breaker (برای قطع درخواست‌های بی‌نتیجه)، Bulkhead (برای محدود کردن تعداد تردهای همزمان)، و Rate Limiter (برای کنترل نرخ درخواست‌ها) را فراهم می‌کند تا سرویس در زمان افزایش بار، کاملاً از کار نیفتد."

Micrometer (برای جمع‌آوری متریک‌های Auto-Scaling): "برای جمع‌آوری معیارهای مورد نیاز Auto-Scaling (مثل cpu.usage، queue.length، و request.count) از Micrometer استفاده می‌کنیم. این متریک‌ها را در اختیار ابزارهایی مثل Prometheus یا CloudWatch قرار می‌دهیم تا تصمیم‌گیری Scaling بر اساس داده‌های واقعی انجام شود."

Spring Cloud Kubernetes یا AWS SDK (برای انجام عملیات Scaling): "برای تعامل با زیرساخت ابری و تغییر تعداد نمونه‌ها، از Spring Cloud Kubernetes (با KubernetesClient و @EnableKubernetes) یا AWS SDK (برای تغییر تعداد Instances در Auto Scaling Group) استفاده می‌کنیم تا عملیات Scaling به‌صورت برنامه‌ریزی‌شده و خودکار انجام شود."

Spring Boot Actuator (برای Graceful Shutdown در Scale Down): "برای پیاده‌سازی Graceful Shutdown در زمان Scale Down، از قابلیت Spring Boot Actuator با تنظیمات management.endpoint.shutdown.enabled=true و server.shutdown=graceful استفاده می‌کنیم. این کار باعث می‌شود که نمونه، ابتدا از دریافت درخواست جدید متوقف شود (Connection Draining)، به درخواست‌های در حال پردازش اجازه‌ی اتمام بدهد (با Timeout مشخص)، و سپس خاموش شود تا کاربر خطا نبیند."

تله‌ها

استفاده از CPU Utilization به‌عنوان تنها معیار Scaling: if (CPU > 70%) scaleUp(); // ❌ ممکن است CPU پایین باشد اما Queue Length بالا باشد (مثلاً به دلیل I/O یا شبکه). باید از ترکیب چند معیار استفاده کنید.

عدم استفاده از Cooldown Period: هر ۱۰ ثانیه معیارها را بررسی کن // ❌ این کار باعث Thrashing می‌شود. باید بین هر Scaling حداقل ۳-۵ دقیقه صبر کنید (Cooldown).

Scale Down بدون در نظر گرفتن درخواست‌های در حال پردازش: System.exit(0); // ❌ درخواست‌های جاری را قطع می‌کند باید از Graceful Shutdown با server.shutdown=graceful و spring.lifecycle.timeout-per-shutdown-phase=30s استفاده کنید.

Hard-Coded کردن آستانه‌ها در کد: if (queueLength > 1000) // ❌ عدد ۱۰۰۰ در کد ثابت است باید آستانه‌ها در application.yml یا Environment Variables تعریف شوند تا بدون Deploy قابل تغییر باشند.

۲. برای هم‌روندی (Concurrency) حتماً synchronized یا FileLock بگذار اگر چند ترد همزمان در حال نوشتن لاگ در یک فایل هستند، حتماً متد logToFile را synchronized کن تا فایل خراب (Corrupt) نشود. نکته‌ی طلایی: Files.writeString با APPEND به‌تنهایی در محیط هم‌روند امن نیست؛ باید از synchronized برای ترتیب‌دهی نوشتن استفاده کنی.

۳. برای تشخیص تراکنش‌ها در گزارش، از یک الگوی ثابت (Prefix) استفاده کن (مثلاً "TRX:") برای تولید گزارش آماری دقیق، هرگز به کلماتی مثل "successful" یا "failed" اکتفا نکن، چون ممکن است در پیام‌های خطا هم تکرار شوند. تمام تراکنش‌ها را با یک پیشوند استاندارد مثل "TRX:" شروع کن. سپس در generateReport فقط خطوط حاوی این پیشوند را فیلتر کن. نکته‌ی طلایی: با این کار، total دقیقاً برابر تعداد تراکنش‌ها می‌شود و خطوط سیستمی (DEBUG و INFOهای معمولی) در آمار لحاظ نمی‌شوند.

۴. پیام‌های ERROR را قابل‌اجرا (Actionable) کن شرط اصلی Accessibility برای کاربر غیرفنی این است که بداند «الان باید چکار کند؟». در پیام‌های ERROR، همیشه یک راهنمای عملی اضافه کن. مثلاً: " | Action: Check transaction ID and retry, or contact support." نکته‌ی طلایی: این کار، لاگ را از یک متن صرفاً اطلاعاتی به یک دستورالعمل عملیاتی تبدیل می‌کند که ارزش Accessibility را چندین برابر بالا می‌برد.

۵. در گزارش‌دهی (Report)، از total == 0 محافظت کن تا NaN نزنی اگر هیچ تراکنشی پردازش نشده باشد، total برابر صفر است و success / total * 100 می‌شود NaN یا Infinity. نکته‌ی طلایی: همیشه از یک شرط if (total == 0) percentage = 0.0 استفاده کن تا خروجی گزارش همیشه یک عدد معتبر باشد.

۶. آرگومان‌ها (args) را با کاما و فاصله (", ") از هم جدا کن آرگومان‌های ورودی لاگ را نباید پشت سر هم بدون جداکننده چسباند. استفاده از for با شرط if (i > 0) sb.append(", ") باعث می‌شود خروجی args خوانا و حرفه‌ای به نظر برسد. نکته‌ی طلایی: خوانایی لاگ، یکی از ارکان اصلی Accessibility است؛ لاگ باید برای چشم انسان (و نه فقط ماشین) خواناترین حالت ممکن را داشته باشد.

۷. معماری Accessibility یعنی «مخاطب‌شناسی» در طراحی خروجی DEBUG: فقط برای توسعه‌دهندگان (جزئیات فنی کامل). INFO: برای اپراتورها (خلاصه‌ی وضعیت، تراکنش‌های موفق). ERROR: برای همه (مدیران، اپراتورها، پشتیبانی) همراه با راهنمای عملی. نکته‌ی طلایی: یک سیستم با Accessibility بالا، نیازی به همراه داشتن مستندات جداگانه برای درک لاگ‌های خود ندارد. خود لاگ‌ها باید «خودتوضیح» (Self-Descriptive) باشند. خلاصه‌ی یک‌خطی برای روز آزمون (Cheat Sheet): «سطوح را با Enum و Index جدا کن، با volatile تغییر پویا بده، با synchronized بنویس، با Prefix (TRX:) گزارش بگیر، به ERROR راهنمای عملی اضافه کن، از تقسیم بر صفر جلوگیری کن، و آرگومان‌ها را خوانا بنویس.»

آیا داده‌های بایگانی‌شده با فرمت فشرده و بهینه (مثل Parquet، ORC، یا فایل‌های Zip) ذخیره می‌شوند تا هزینه‌ی ذخیره‌سازی کاهش یابد؟ (اگر داده‌ها بدون فشرده‌سازی در S3 استاندارد بمانند → هزینه بالا می‌رود).

آیا قابلیت بازیابی (Retrieval) داده‌های بایگانی‌شده در بازه‌ی زمانی تعیین‌شده (مثلاً کمتر از ۴ ساعت) وجود دارد و فرایند آن برای کاربر شفاف است؟ (اگر بازیابی ممکن نباشد یا زمان آن بیش از حد مجاز باشد → ویژگی بایگانی بی‌فایده است).

آیا برای داده‌های بایگانی‌شده ایندکس یا متادیتا (مثل بازه‌ی زمانی، شناسه‌ی مشتری) نگهداری می‌شود تا جستجو و بازیابی سریع باشد؟ (اگر فقط فایل‌های خام ذخیره کنید → پیدا کردن داده‌ی خاص مانند "پیدا کردن سوزن در انبار کاه" است).

کلمات کلیدی

Data Lifecycle Management (مدیریت چرخه‌ی حیات داده): "داده‌ها در طول زمان ارزش خود را از دست می‌دهند؛ بنابراین باید سیاستی تعریف کنیم که داده‌های سرد را به‌طور خودکار به ذخیره‌سازی ارزان‌تر و با دسترسی کمتر منتقل کند و در صورت نیاز، امکان بازیابی مجدد را فراهم آورد."

Storage Tiering (لایه‌بندی ذخیره‌سازی): "برای بهینه‌سازی هزینه و عملکرد، داده‌ها را در لایه‌های مختلف (Hot → Warm → Cold → Archive) قرار می‌دهیم. داده‌های بایگانی‌شده در ارزان‌ترین لایه (مثل S3 Glacier یا Tape) ذخیره می‌شوند."

Retrieval Time Objective (RTO برای بازیابی): "برای داده‌های بایگانی‌شده، باید یک هدف زمانی برای بازیابی (مثلاً کمتر از ۴ ساعت) تعریف کنیم تا در صورت نیاز به داده‌های قدیمی، بتوانیم آنها را در بازه‌ی قابل‌قبولی برگردانیم."

Immutable Storage (ذخیره‌سازی تغییرناپذیر): "داده‌های بایگانی‌شده نباید تغییر کنند. برای رعایت مقررات (مثل GDPR یا حسابداری)، باید از ذخیره‌سازی غیرقابل تغییر استفاده کنیم تا کسی نتواند داده‌های قدیمی را دستکاری کند."

تله‌ها

بایگانی همزمان با تراکنش‌های اصلی: archiveOldData(); // ❌ در همان ترد درخواست کاربر اجرا می‌شود باید این کار را به یک Job یا Scheduler شبانه بسپارید.

حذف داده‌های اصلی بدون تأیید موفقیت‌آمیز بودن بایگانی: اگر داده را از دیتابیس اصلی پاک کنید اما به ذخیره‌سازی سرد نرسد → داده برای همیشه از دست می‌رود. deleteFromMainDB(); // ❌ قبل از اطمینان از ذخیره‌سازی ذخیره‌سازی بدون فشرده‌سازی (فقط به‌صورت JSON یا CSV خام): حجم داده‌ها را چندین برابر افزایش می‌دهد و هزینه‌ی سربار (Egress/Ingress) را بالا می‌برد.

نداشتن متادیتا یا ایندکس برای داده‌های بایگانی‌شده: اگر فقط فایل‌ها را در S3 بگذارید و هیچ جدولی از محتویات آنها نداشته باشید → بازیابی یک رکورد خاص روزها طول می‌کشد.

عدم تست بازیابی (Recovery Drill): اگر هرگز بازیابی را تست نکنید، ممکن است در زمان واقعی متوجه شوید که فایل‌ها آسیب دیده، رمزنگاری نشده، یا فرمت آن‌ها تغییر کرده است.

خلاصه

Archiveability یعنی "قابلیت انتقال خودکار، فشرده، و امن داده‌های قدیمی به ذخیره‌سازی ارزان‌تر، بدون تأثیر بر عملکرد سیستم و با قابلیت بازیابی در زمان معقول". برای رسیدن به آن، یک سیاست چرخه‌ی حیات تعریف کنید که داده‌های سرد را بر اساس زمان (مثلاً ۶ ماه) شناسایی کند. عملیات بایگانی را در پنجره‌ی کم‌بار (شب) و به‌صورت غیرهمزمان انجام دهید تا به کاربران لطمه نزند. داده‌ها را با فرمت فشرده (Parquet) ذخیره کنید و برای هر بسته‌ی بایگانی، متادیتا (بازه‌ی زمانی، تعداد رکوردها، نوع داده) را در دیتابیس نگهداری کنید تا جستجو و بازیابی سریع باشد. همیشه قابلیت بازیابی را با RTO مشخص (مثلاً ۴ ساعت) تضمین کنید و قبل از حذف داده از منبع اصلی، از موفقیت‌آمیز بودن انتقال به ذخیره‌سازی سرد اطمینان حاصل کنید (Two-Phase Commit یا حداقل تأیید MD5). در نهایت، به‌طور دوره‌ای تمرین بازیابی انجام دهید تا مطمئن شوید داده‌ها در دسترس و سالم هستند.

کلمات کلیدی

🔑 نکته‌ی طلایی ۱: "Checkpoint بعد از موفقیت، نه قبل از آن" وضعیت را فقط پس از پردازش موفق یک تراکنش ذخیره کن. اگر قبل از موفقیت ذخیره کنی، در صورت شکست، آن تراکنش برای همیشه از دست می‌رود (چون دیگر در لیست پردازش قرار نمی‌گیرد).

🔑 نکته‌ی طلایی ۲: "اگر یک تراکنش شکست خورد، نقطه‌بازرسی را جلو نبر" تا زمانی که یک تراکنش با خطا مواجه شده، نقطه‌بازرسی را به‌روز نکن تا در اجرای بعدی، تراکنش‌های قبل از خطا دوباره امتحان شوند (یا حداقل از قلم نیفتند).

🔑 نکته‌ی طلایی ۳: "هر نوشتن، باید اتمی باشد" الگوی Write to temp → Atomic Move را همیشه رعایت کن. هرگز مستقیم روی فایل وضعیت TRUNCATE_EXISTING نزن، چون در لحظه‌ی کرش، فایل خراب (Corrupt) می‌شود.

🔑 نکته‌ی طلایی ۴: "تراکنش‌های شکست‌خورده باید روی دیسک ذخیره شوند، نه فقط در حافظه" لیست failedTransactions در حافظه، با یک kill -9 از بین می‌رود. این‌ها باید در یک فایل جداگانه (*.failed) با APPEND ذخیره شوند تا در اجرای بعدی دوباره پردازش شوند.

🔑 نکته‌ی طلایی ۵: "اگر هر دو فایل وضعیت خراب بودند، خطا بده، نه بازگشت به صفر" بازگشت به صفر یعنی پردازش دوباره‌ی همه‌ی تراکنش‌ها که ممکن است فاجعه‌بار باشد (مثلاً پرداخت دوباره). بهتر است یک IOException واضح پرتاب کنی تا اپراتور مداخله کند.

🔑 نکته‌ی طلایی ۶: "برای سیستم‌فایل‌های قدیمی، Fallback داشته باش" ATOMIC_MOVE در NFS یا برخی سیستم‌فایل‌های قدیمی پشتیبانی نمی‌شود. در catch مربوطه، یک Files.move ساده (بدون ATOMIC_MOVE) به‌عنوان Fallback بگذار.

🔑 نکته‌ی طلایی ۷: "هم‌روندی را جدی بگیر" اگر processAll از چند ترد صدا زده شود، بدون synchronized یا FileLock، فایل وضعیت خراب می‌شود. این یک نقص حیاتی در Recoverability است.

🔑 نکته‌ی طلایی ۸: "در صورت خطای دیسک، پردازش را متوقف کن، نه نادیده بگیر" اگر Files.writeString یا Files.move با IOException مواجه شد، این یعنی وضعیت ذخیره نشده و آن تراکنش از دست رفته است. اینجا باید استثنا را به بالا پرتاب کنی (یا حداقل به لیست failedTransactions اضافه کنی)، نه اینکه فقط لاگ بزنی و رد شوی.

☠️ تله‌ی مرگبار ۷: تقسیم بر صفر (success / total) اگر هیچ تراکنشی پردازش نشده باشد، total=0 و نتیجه NaN می‌شود. این باگ در گزارش‌های تولیدی، می‌تواند به تصمیمات اشتباه منجر شود.

☠️ تله‌ی مرگبار ۸: تقسیم بر صفر در محاسبه‌ی درصد موفقیت java double percentage = (double) success / failed; اگر failed=0 باشد، نتیجه Infinity می‌شود، نه ۱۰۰٪. فرمول درست: success / total * 100.

۱. "غیرتهاجمی بودن" (Non-Intrusiveness) را جدی بگیر قابلیت‌های پشتیبانی (مانند گزارش وضعیت، تغییر سطح لاگ، خاموشی) هرگز نباید ترد اصلی برنامه را مسدود کنند. از ScheduledExecutorService برای کارهای دوره‌ای و از تردهای جداگانه (Daemon Thread) برای گوش‌دادن به دستورات استفاده کن. نکته‌ی طلایی: اگر ترد پشتیبانی join() یا awaitTermination() کند و ترد اصلی منتظر آن بماند، طراحی شما شکست خورده است. پشتیبانی باید در پس‌زمینه اجرا شود.

۲. مدیریت خاموشی امن (Graceful Shutdown) با volatile boolean برای خاموش کردن ترد پشتیبانی، از یک پرچم volatile boolean running استفاده کن. در ترد پشتیبانی، حلقه‌ی اصلی را با while (running) کنترل کن تا با تغییر پرچم، ترد به‌خوبی پایان یابد. از Runtime.getRuntime().addShutdownHook() برای خاموشی امن در هنگام بسته‌شدن JVM استفاده کن. نکته‌ی طلایی: shutdownNow() را با awaitTermination(5, TimeUnit.SECONDS) ترکیب کن تا به ترد فرصت پاک‌سازی بدهی، نه اینکه ناگهان قطعش کنی.

۳. ارائه‌ی وضعیت (Status) در قالب یک گزارش جامع و خودتوضیح گزارش وضعیت باید حداقل شامل این ۴ بخش باشد: Uptime: زمان فعالیت سیستم بر حسب ثانیه ((System.currentTimeMillis() - startTime) / 1000) آمار کسب‌وکار: تعداد تراکنش‌های موفق/ناموفق (از یک Counter هم‌روند) وضعیت منابع: حافظه‌ی استفاده‌شده (Runtime.getRuntime().totalMemory() - freeMemory()) وضعیت پیکربندی: سطح فعلی لاگ، وضعیت اتصالات، یا هر پارامتر مدیریتی دیگر نکته‌ی طلایی: وضعیت باید انسانی‌خوان (Human-Readable) باشد، نه فقط یک سری اعداد خام. از String.format برای تولید گزارش تمیز استفاده کن.

۴. مکانیزم دریافت دستور بدون نیاز به پورت (برای محیط‌های محدود) در محیط‌هایی که نمی‌توانی پورت باز کنی (مثل Docker با محدودیت پورت)، از فایل سیگنال (Signal File) استفاده کن: ایجاد یک پوشه‌ی مشخص مثل /var/run/myapp/ و گوش‌دادن به فایل‌های signal.status و signal.stop. با ScheduledExecutorService هر N ثانیه یک‌بار پوشه را چک کن و در صورت وجود فایل، دستور را اجرا و سپس فایل را پاک کن. نکته‌ی طلایی: فایل سیگنال را با Atomic Move یا Files.deleteIfExists اتمیک حذف کن تا در اثر چند بار چک کردن، دستور دوبار اجرا نشود.

۵. پاسخ‌دهی به دستورات به‌صورت اتمیک (با synchronized) اگر چند دستور همزمان (یا چند درخواست Socket) دریافت شوند، پردازش آن‌ها باید اتمی باشد: متدهای مدیریتی (مثل writeStatus(), stop(), setLogLevel()) را synchronized کن. اگر از Socket استفاده می‌کنی، هر اتصال را در یک ترد جداگانه پردازش کن اما خود دستور را با یک قفل (ReentrantLock) محافظت کن. نکته‌ی طلایی: استفاده از synchronized روی متدهای مدیریتی، ساده‌ترین و مؤثرترین راه برای جلوگیری از شرایط رقابتی (Race Condition) است.

۶. گزارش‌دهی‌های خود را به یک فایل لاگ جداگانه یا کنسول بفرست پیام‌های مربوط به پشتیبانی (مثل "Status written." و "Shutting down...") باید از لاگ اصلی جدا باشند تا تیم پشتیبانی را گیج نکنند. می‌توانی از System.out برای این پیام‌ها استفاده کنی (چون سطح Accessible هستند)، یا یک فایل جداگانه مثل support.log بنویسی. نکته‌ی طلایی: اگر از لاگر اصلی استفاده می‌کنی، پیام‌های پشتیبانی را با سطح INFO یا WARN ثبت کن تا در لاگ‌های تولید گم نشوند.

۷. خودتمیزی (Self-Cleanup) را فراموش نکن پس از خاموشی، تمام منابع (Socket، ExecutorService، فایل‌های باز) را ببند. اگر ScheduledExecutorService داری، حتماً shutdown() و awaitTermination() را در متد stop() صدا بزن. اگر فایل موقتی برای سیگنال‌ها ایجاد کرده‌ای، آن را در هنگام خاموشی پاک کن. نکته‌ی طلایی: یک ShutdownHook همیشه برای مواقعی که stop() به‌درستی صدا زده نشده (مثل kill -9) مفید است، اما به آن اعتماد نکن؛ stop() را همیشه در جریان عادی فراخوانی کن.

Configurability

نکات

۱. اصل «جداسازی پیکربندی از کد» (External Configuration Principle) کد باید کاملاً از نحوه‌ی تأمین مقادیر بی‌خبر باشد. فرقی نمی‌کند مقدار از فایل بیاید، از Environment Variable بیاید، یا از یک سرویس مرکزی (مثل Consul یا Vault). کلاس شما (AlertConfiguration) فقط یک تأمین‌کننده‌ی مقدار (Value Provider) است و منطق کسب‌وکار (AlertService) هرگز نباید بداند که مقدار از کجا آمده است. شما این کار را با Constructor Injection به خوبی انجام دادید.

۲. سلسله‌مراتب اولویت (Overriding Hierarchy) را دقیقاً مشخص کنید در محیط‌های مدرن، مقادیر از منابع مختلف می‌آیند. قانون طلایی من در Handbook این است: آرگومان خط فرمان > متغیر محیطی > فایل پیش‌فرض > مقدار Hard-Coded در کد شما این را دقیقاً با System.getProperty → System.getenv → application.properties پیاده‌سازی کردید. این یعنی اپراتور DevOps می‌تواند بدون تغییر فایل، با یک آرگومان ساده، سیستم را اورراید کند.

۳. «Fail-Safe» باشید، نه «Fail-Fast» (مگر در موارد امنیتی) سیستم نباید به خاطر نبود یک فایل کانفیگ از کار بیفتد. شما با پیش‌فرض‌های منطقی (DEFAULT_...) این کار را کردید. تنها استثنا، کلیدهای امنیتی (مانند رمزعبور بانکی) هستند که اگر نباشند، بهتر است سیستم با Fail-Fast متوقف شود تا امنیت به خطر نیفتد. اما برای تنظیمات معمولی مثل سطح لاگ یا تعداد تلاش مجدد، Fail-Safe درست است.

۴. از java.util.Properties استاندارد استفاده کنید (نه readAllLines) شما این کار را عالی انجام دادید. Properties از Encoding پیش‌فرض، = و : به عنوان جداکننده، و کامنت‌گذاری با # پشتیبانی می‌کند. این یک استاندارد جاواست که نیازی به کتابخانه‌ی خارجی ندارد و در آزمون شما دقیقاً همین را می‌خواهند.

۵. «نوع‌ایمنی (Type Safety)» را در لایه‌ی کانفیگ تضمین کنید متدهای getter باید تضمین کنند که داده را با نوع درست برمی‌گردانند. اگر عددی در فایل به اشتباه "سه" نوشته شده باشد، متد getMaxRetryCount باید با NumberFormatException برخورد کند و پیش‌فرض را برگرداند (که شما با متد کمکی getInt این کار را کردید). این کار از خراب شدن کل سیستم در زمان اجرا جلوگیری می‌کند.

۷. امنیت اطلاعات (Secrets Management) هیچ‌گاه رمزعبور یا توکن را به صورت Plain Text در فایل application.properties نسپارید. در راه‌حل استاندارد، یا باید از رمزگذاری (Encryption) استفاده کنید (مثلاً با Cipher) و کلید را از Environment Variable بگیرید، یا از ابزارهای خارجی مانند Vault استفاده کنید. در پاسخ‌های تشریحی آزمون، حتماً به این نکته اشاره کنید که برای محیط تولید، فایل Properties نباید حاوی اطلاعات حساس باشد.

۸. تست‌پذیری با تزریق وابستگی (Dependency Injection for Testing) شما با دو سازنده (AlertService() و AlertService(AlertConfiguration)) این کار را کردید. این یعنی در تست‌های واحد، می‌توانید یک Mock از AlertConfiguration بسازید و رفتارهای مختلف (فایل خراب، مقدار نامعتبر، فایل موجود) را بدون نیاز به ایجاد فایل واقعی روی دیسک، تست کنید.

۹. خطاهای خواندن فایل را لاگ کنید، اما اجرا را متوقف نکنید در catch (IOException e) شما فقط System.err.println کردید. این عالی است، اما در سطح حرفه‌ای، بهتر است این خطا را با یک Logger معروف (مثل java.util.logging یا SLF4J - اگرچه در آزمون ممنوع است ولی در طراحی باید بدانید) ثبت کنید تا اپراتور بتواند مشکل را در لاگ‌ها ببیند.

خلاصه‌ی طلایی(۴ کلمه): اگر سوالی با NFR = Configurability آمد، این ۴ کلمه را در ذهن داشته باشید: Externalize (خارج‌سازی از کد) Default (همیشه پیش‌فرض داشته باش) Priority (اولویت منابع را رعایت کن) Type-safe (نوع داده‌ها را در Getter مدیریت کن)

Localization

نکات

۱. اصل "جداسازی کامل متن از کد" (Separation of Concerns) قانون طلایی: هیچ‌گاه متن‌های نمایشی را در کد Hard-Code نکنید. شما با ResourceBundle این کار را کردید. اما نکته‌ی مهم این است که حتی خطوط خالی، فاصله‌ها و نشانه‌های نگارشی نیز باید در فایل‌های Properties قرار گیرند، نه در کد. نکته‌ی Lead: "کد شما باید بدون هیچ متنی (به جز لاگ‌های سیستمی) قابل اجرا باشد. همه‌چیز باید از فایل‌های Properties بیاید."

۲. اصل "فرمت‌کننده‌های استاندارد جاوا" (Standard Formatters) شما از DateFormat و NumberFormat.getCurrencyInstance استفاده کردید که کاملاً درست است. اما نکته‌ی طلایی این است که هرگز از SimpleDateFormat با الگوی ثابت (مثلاً "yyyy/MM/dd") استفاده نکنید، زیرا این کار انعطاف‌پذیری را از بین می‌برد. همیشه از متدهای getDateInstance، getTimeInstance، و getDateTimeInstance با سبک‌های SHORT, MEDIUM, LONG, FULL استفاده کنید. نکته‌ی Lead: "اگر الگوی تاریخ را خودتان تعیین کنید، برای کشورهای دیگر (مثل آمریکا که ماه/روز/سال است) اشتباه خواهد بود. بگذارید خودِ Locale تصمیم بگیرد."

۳. اصل "ارز و اعداد با CurrencyInstance نه NumberInstance" شما از NumberFormat.getCurrencyInstance استفاده کردید که عالی است. نکته‌ی مهم این است که getNumberInstance فقط عدد را فرمت می‌کند (با جداکننده‌های هزارگان) ولی نماد ارز را نمایش نمی‌دهد. اگر از CurrencyInstance استفاده کنید، جاوا به‌صورت خودکار: نماد ارز ($, €, ¥, £) را بر اساس Locale انتخاب می‌کند. جایگاه نماد را (قبل یا بعد از عدد) به‌درستی تنظیم می‌کند (مثلاً در فرانسه 1 250,50 € و در آمریکا $1,250.50). جداکننده‌های هزارگان و اعشار را به‌درستی اعمال می‌کند.

۴. اصل "استفاده از MessageFormat برای پارامترهای پویا" اگر متن‌های شما شامل پارامترهایی مانند {0}, {1} هستند، از MessageFormat استفاده کنید. این کار: جایگزینی پارامترها را به‌صورت استاندارد انجام می‌دهد. از ChoiceFormat برای انتخاب جمع/مفرد (مثلاً 1 item در مقابل 2 items) پشتیبانی می‌کند. به مترجم اجازه می‌دهد که جایگاه پارامترها را در جمله تغییر دهد (در زبان‌های مختلف ترتیب کلمات متفاوت است).

مثال: properties invoice.message=Dear {0}, your order of {1,number,currency} has been confirmed. java String msg = MessageFormat.format(bundle.getString("invoice.message"), customerName, amount); ۵. اصل "مدیریت Locale در لایه‌ی درخواست (Request Scope)" در برنامه‌های وب، Locale باید از درخواست کاربر (مثلاً هدر Accept-Language مرورگر) گرفته شود، نه اینکه در کد Hard-Code شود. در کد شما، Locale را به‌عنوان پارامتر به سازنده می‌دهید که درست است، اما در برنامه‌های واقعی، این Locale باید پویا باشد.

۶. اصل "Fallback یا سقوط به عقب" (با سلسله‌مراتب ResourceBundle) ResourceBundle به‌صورت خودکار یک سلسله‌مراتب را دنبال می‌کند: زبان + کشور (مثلاً Messages_fr_CA) فقط زبان (مثلاً Messages_fr) زبان پیش‌فرض سیستم (مثلاً Messages_en) در نهایت، اگر هیچ‌کدام موجود نبود، MissingResourceException پرتاب می‌شود. نکته‌ی Lead: "همیشه یک فایل پیش‌فرض (مثلاً Messages_en.properties) داشته باشید تا در صورت نبود فایل زبان کاربر، برنامه از کار نیفتد." ۷. اصل "تست Localization در زمان اجرا" برای تست Localization، از Locale.setDefault() برای تغییر موقت Locale سیستم استفاده کنید و تست‌های واحد بنویسید:

Locale.setDefault(Locale.FRANCE); // کد شما اما توجه کنید که این کار برای تست‌های واحد ایمن است، نه برای محیط تولید.

۸. اصل "مدیریت فایل‌های Properties با Encoding صحیح" فایل‌های Properties به‌صورت پیش‌فرض با ISO-8859-1 (Latin-1) ذخیره می‌شوند که از کاراکترهای غیرانگلیسی (مانند é, ä, ç) پشتیبانی نمی‌کند. برای پشتیبانی از UTF-8، باید در هنگام بارگذاری، Charset را مشخص کنید (در جاوا ۹ به بعد):

ResourceBundle bundle = ResourceBundle.getBundle("Messages", locale, Control.INSTANCE); یا از ابزار native2ascii برای تبدیل استفاده کنید.

خلاصه‌ی طلایی (۴ کلمه): اگر سوالی با NFR = Localization آمد، این ۴ کلمه را در ذهن داشته باشید: Bundle (استفاده از ResourceBundle) Format (استفاده از DateFormat و NumberFormat) Locale (تعیین Locale پویا) Separate (جداسازی کامل متن از کد)

Reusability

نکات

۱. اصل "وابستگی به انتزاع، نه به جزئیات" (Dependency Inversion) قانون طلایی: کلاس شما نباید بداند که داده از کجا آمده است (فایل، دیتابیس، REST، یا حتی سرویس ابری).

۲. اصل "ترکیب بر ارث‌بری" (Favor Composition over Inheritance) ارث‌بری (extends) کلاس را به یک پیاده‌سازی خاص گره می‌زند. در کد اولیه‌ی شما، همه‌ی استراتژی‌ها از AbstractCalculator ارث‌بردند و به فایل products.txt وابسته شدند.

۳. اصل "جداسازی لاگ و گزارش‌گیری از منطق کسب‌وکار" در کد اولیه، چاپ System.out.println در دل DiscountEngine بود. این یعنی هر پروژه‌ای که از این کتابخانه استفاده کند، مجبور است خروجی را در کنسول ببیند.

۴. اصل "کشف خودکار (Discovery) با ServiceLoader" در کتابخانه‌های سطح بالا، نمی‌خواهیم که مصرف‌کننده مجبور باشد همه‌ی استراتژی‌ها را با new بسازد. استفاده از ServiceLoader باعث می‌شود که با اضافه کردن یک JAR جدید به Classpath، استراتژی جدید به صورت خودکار شناسایی شود (مانند JDBC Driverها).

۵. اصل "کمترین دانسته‌ها (Principle of Least Knowledge)" یک کلاس قابل استفاده‌ی مجدد نباید بیش از حد بداند. مثلاً VipDiscountStrategy نباید بداند که VIP_CUSTOMERS در کجا ذخیره شده است. فقط باید یک boolean isVip دریافت کند و تخفیف را محاسبه کند.

۶. طراحی برای "بسته‌بندی مستقل" (Modular JAR) برای استفاده‌ی مجدد واقعی، کتابخانه باید یک JAR مستقل باشد که هیچ وابستگی به کتابخانه‌های خارجی (مثل Spring یا Hibernate) نداشته باشد. در کد ۱۰ شما، فقط از java.util.* و java.function.* استفاده شد، که یعنی همین کد را می‌توانید در یک پروژه‌ی Spring Boot، یک اپلیکیشن JavaFX، یا حتی یک برنامه‌ی کامندلاین استفاده کنید.

۷. اصل "ورودی/خروجی تابعی (Functional I/O)" اگر کتابخانه‌ی شما نیاز به دریافت داده دارد، آن را به شکل Function یا Supplier دریافت کنید، نه به شکل File یا Connection. این کار به مصرف‌کننده اجازه می‌دهد که داده را از هر جایی (حتی از یک سرویس شبکه) تأمین کند.

خلاصه‌ی طلایی (۴ کلمه):

اگر سوالی با NFR = Reusability آمد، این ۴ کلمه را در ذهن داشته باشید:

Abstraction (وابسته به اینترفیس باش، نه کلاس)

Injection (وابستگی‌ها را از بیرون به کلاس بده)

Separation (منطق را از داده و لاگ جدا کن)

Stateless (استراتژی‌ها را بی‌حالت و ناب (Pure) نگه دار)

Upgradbility

نکات

۱. اصل "نسخه‌گذاری در لایه‌ی داده (Data Versioning)" قانون طلایی: فرمت داده‌ها (فایل، دیتابیس، یا پیام) باید همیشه یک شناسه‌ی نسخه (Version Header) در خود داشته باشد. شما در کدتان این کار را با #Version2 انجام دادید. این یعنی فایل، خودش به کتابخانه می‌گوید که با چه زبانی نوشته شده است.

۲. اصل "تغییرات افزاینده (Additive Changes)" نه "تغییرات مخرب (Breaking Changes)" اگر قرار است فرمت جدیدی اضافه کنید، هرگز متدهای قدیمی را حذف یا تغییر ندهید. همیشه یک متد/مسیر جدید اضافه کنید و متد قدیمی را @Deprecated کنید (در کد شما، این یعنی اضافه کردن loadV2 در کنار loadV1).

۳. اصل "سازگاری معکوس (Backward Compatibility) واجب، سازگاری پیشرو (Forward Compatibility) امتیاز مثبت" سازگاری معکوس (Backward): کتابخانه‌ی جدید (v2) باید فایل‌های قدیمی (v1) را بخواند. (شما این را با else در load پیاده‌سازی کردید). سازگاری پیشرو (Forward): اگر کتابخانه‌ی قدیمی (v1) یک فایل جدید (v2) را بخواند، نباید کرش کند. (در کد شما، اگر کتابخانه‌ی V1 فایل V2 را بخواند، خط اول #Version2 را به عنوان یک کلید معمولی (#Version2=...) می‌خواند که شاید خراب نشود، اما ایده‌آل نیست؛ برای سطح Lead، پیشنهاد می‌کنم کتابخانه‌ی V1 حداقل خطوط ناشناخته را نادیده بگیرد).

۴. اصل "مهاجرت (Migration) در لایه‌ی خواندن (Read)، نه در لایه‌ی ذخیره‌سازی (Write)" در کد شما، وقتی کتابخانه‌ی V2 یک فایل V1 را می‌خواند، آن را به ساختار جدید تبدیل می‌کند، اما فایل فیزیکی روی دیسک را تغییر نمی‌دهد (مگر اینکه کاربر save را صدا بزند).

۵. اصل "مدیریت خطاهای ناشی از نسخه‌ی ناشناخته (Unknown Version)" اگر فایل هدری داشت که کتابخانه نمی‌شناخت (مثلاً #Version3 که هنوز ساخته نشده)، کتابخانه نباید با NullPointerException یا NumberFormatException کرش کند. باید یک استثنای معنادار (مثل UnsupportedVersionException) پرتاب کند تا تیم توسعه بداند که باید کتابخانه را ارتقاء دهند.

۶. اصل "تست‌پذیری نسخه‌ها (Version Matrix Testing)" در سطح Lead، شما باید یک ماتریس تست داشته باشید که ترکیب‌های مختلف (کتابخانه V1 با فایل V1، کتابخانه V1 با فایل V2، کتابخانه V2 با فایل V1، کتابخانه V2 با فایل V2) را پوشش دهد. کد شما در load با if-else ساده این کار را ممکن می‌کند.

۷. اصل "ارتقاء تدریجی (Phased Rollout)" کتابخانه‌ی شما باید طوری طراحی شود که پروژه‌ها بتوانند یکی‌یکی (بدون وابستگی به هم) به نسخه‌ی جدید بروند. با ذخیره‌سازی در نسخه‌ی جدید (save که همیشه #Version2 را می‌نویسد)، به مرور تمام فایل‌های سیستم به نسخه‌ی ۲ مهاجرت می‌کنند، بدون اینکه یک‌باره همه‌چیز متوقف شود. نکته‌ی Lead: "ارتقاء یک ماراتون است، نه یک دوی سرعت. کتابخانه‌ی شما باید چندین ماه بتواند با هر دو نسخه کنار بیاید تا تیم‌ها فرصت مهاجرت داشته باشند."

خلاصه‌ی طلایی (۴ کلمه):

Header (هدر نسخه در داده)

Backward (سازگاری با گذشته)

Ignore (نادیده گرفتن داده‌های ناشناخته)

Migration (مهاجرت تدریجی در لایه‌ی خواندن)
